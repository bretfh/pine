#+TITLE: pine: help and self-documentation
#+AUTHOR: Bret Horne
#+OPTIONS: toc:2 num:t

* Why this document exists

The feature that made Emacs learnable from inside is that every
question about the system is answered BY the system: describe any key,
any function, any variable, and jump from the answer to the source.
pine already committed to the seed of this -- every ask target answers
:describe with its verb list, every defonce carries documentation,
docstrings are enforced across the tree -- and the discipline has paid
for itself repeatedly: the API stayed honest because it could be
interrogated. This document prescribes growing that seed into
describe-anything, and states the rule that keeps it true.

* The rule

Help is a query against the live system, never prose beside it. A help
buffer is computed at ask time from the registries and docstrings of
the running image -- if it can drift from the code, it is built wrong.
The org files (doc/, design/) describe intent and architecture; what a
thing IS right now, only the image may answer.

* What exists, named

- (ask TARGET :describe) on :server, :client, :project (charted), and
  every buffer -- the verb lists.
- describe-key (%describe-key-text, editor.lisp): what a key runs,
  now correct across keymaps since chords resolve against every
  active map.
- %bindings-text / %variables-text (editor.lisp): the active bindings
  and declared variables as text with docstrings.
- defonce :documentation, defcommand docstrings, mode indicators, the
  faces and modes registries on the server, store keys inspectable
  from scratch.

* Charted

- describe-command / describe-function / describe-variable /
  describe-mode / describe-key as layout buffers (show-layout), not
  echo strings: name, docstring, bindings that reach it, mode that owns
  it, and a source jump via the intelligence :definition verb -- help
  and intelligence share that seam, which is why help deepens as
  intelligence lands.
- apropos: one prompt, matching over every registry at once --
  commands, variables, modes, faces, refs, buffer verbs, store keys --
  results grouped by kind in a layout buffer, Return describes,
  M-. jumps. The orderless completion engine already ranks; apropos is
  a candidates producer over the registries.
- bindings and variables become interactive tool buffers: rows,
  Return describes, editable where sensible ((setf (var ...)) from the
  variables buffer with the same prompt machinery).
- The api.org words table becomes queryable: (ask :server :words) or a
  help command rendering it, so the vocabulary is one keystroke away
  when writing init code.
- Every new system's registries join apropos as they land: project
  verbs, vc commands, intelligence producers, world contributors.

* Refused

- Help text maintained by hand anywhere a registry can answer.
- A help mode with its own navigation conventions: help buffers are
  layout buffers with the same selection and Return behavior as every
  other tool.
- Documentation coverage tooling beyond the existing discipline; the
  fix for a missing docstring is writing it.

* Open questions

- Whether describe buffers show the CURRENT effective value/binding
  context (this client, this buffer's modes) or the global view with
  the local diff marked; leaning effective-with-diff, since the locals
  are usually the question.
- Whether apropos should search docstring bodies or names only;
  names-first with a flag is the cheap start.

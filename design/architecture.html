pine

A Lisp Machine substrate shaped like the Emacs daemon. One headless SBCL image owns live, immutable, addressable state and runs computations; separate OS processes attach over the network and render. Within an image it is a Lisp Machine; between images it is Erlang.

1Overview & philosophy

Pine is not an editor with a server bolted on. It is a substrate — a long-lived Lisp image that holds the world — with editing and a desktop as two of its tenants. The defining choice is the split between a single image that owns state and many processes that merely render or compute.

Within an image

A Lisp Machine (Genera / Hemlock). Everything is live, inspectable, and redefinable at runtime. Immutable values are shared by reference in one heap. You author from the editor and every error's restart menu comes home to you.

Between images

Erlang / OTP. Processes are addressable actors connected by async message passing over the network, supervised and respawned. A computation can crash in its own image without touching the daemon or the editor.

fset is the seam. An immutable fset value is a single object shared by reference inside one heap, and it serializes to plain data to cross the wire. That one property is what lets state live in exactly one place (the daemon) and still be present, cheaply, wherever it is needed.

The daemon owns state and never draws. Apps draw and own no state. Agents compute and are disposable. Everything crosses as plain data; only the daemon holds the live objects.

3The daemon

The headless image. It holds the server object (the root of all registries and the actor system), boots every subsystem in a fixed order, and then stays up. It renders buffers to frames and builds surface trees on demand, but it never touches a GPU or a window.

Boot sequence

start-daemon (in src/main.lisp) brings the world up in dependency order:

start-daemon
  → server + remoting            ; the actor-system, listening on :17000
  → ts-runtime + ensure-ts       ; tree-sitter library + language
  → event-bus
  → agent-registry → local-agent → agent-debug actor
  → buffer-registry
  → attach-listener              ; /user/attach — apps connect here
  → faces (install-default-faces) → modes → commands → bindings
  → editor sessions              ; per-app minibuffer/terminal/debug handlers
  → desktop sessions → desktop config   ; register the bar + 5 panels
  → jobs
  → sources                      ; the reactive data feeders (niri/pactl/nmcli/...)

run-daemon wraps this: it first fills WAYLAND_DISPLAY/NIRI_SOCKET from XDG_RUNTIME_DIR (so a service started outside the session still reaches it — see Deployment), starts the daemon, then (loop (sleep 3600)) to stay alive.

The actor system

Everything concurrent is a sento actor. The server holds one actor-system with a shared dispatcher pool. The cardinal rule: blocking IO never runs on the shared pool. Buffer replies, source reads, and widget handlers each run on their own thread, so a slow nmcli or a runaway eval cannot starve the daemon or hang an app. Actors are addressed by URI (sento://host:port/user/name) and talk with async tell — never a blocking ask across the wire.

4State: buffers & fset

Buffers as immutable actors

A buffer is an actor wrapping an immutable buffer-state (fset-backed lines + marks + meta + a tick). Every edit produces a new state; the actor swaps its reference and notifies subscribers. Because the value is immutable, a snapshot handed to a renderer can never be mutated under it — no locks on the read path.

buffer-state = lines · marks · meta · tick
snapshot     = name · line-count · point-line/col · highlights   ; the read view
edit ops:  insert-char/string/newline · delete-char/region · move-mark
each op:   state → state'  (structural sharing; O(edit), not O(buffer))

Editing, undo/redo, tree-sitter state and highlighting live solely in the daemon's buffer layer. Keystrokes remain programmatically sendable (from the app, an agent, or a script), but the buffer and its incremental parser are never shipped over the wire — only snapshots and rendered frames are.

The seam

Inside the daemon a snapshot is a live object shared by reference. To reach an app it is rendered to plain data — the wire carries only keywords, strings, numbers, lists and vectors. fset and CLOS objects are flattened at the edge and never cross intact. This is what keeps "one owner of state" honest: the app holds a picture, never the thing.

5Attach & remoting

An app is its own actor-system with remoting enabled and a single display actor. It attaches to the daemon; from then on all traffic is async tells in both directions.

The handshake

app  → daemon /user/attach : (:attach :display-uri U :kind :editor|:desktop)
daemon:  makes a client bound to a remote-ref to the app's display,
         plus a per-client input actor /user/client-N;
         runs the kind's :on-attach hook.
daemon → app display : (:attached :id N :client-uri "sento://…/user/client-N")
app:     makes a remote-ref to client-uri; sends all input there.

Message tables

app → daemon (client-N)

(:key :key-str S :ctrl B :meta B
      :shift B :super B)      ; editor
(:resize :cols C :rows R)     ; editor
(:widget-action :id N :args …) ; desktop
(:refresh)                   ; desktop
(:hint :text S)             ; desktop

daemon → app (display)

(:frame :cols C :rows R
       :cursor-row cr :cursor-col cc
       :grid ROWS)            ; editor
(:widgets :surface NAME
         :tree DATA)         ; desktop
(:panel :name NAME :show B)   ; desktop

The editor frame wire — row / runs

The daemon renders a buffer to a flat cell grid, then encodes it compactly for the wire:

:grid = list of rows, each (TEXT . RUNS)
RUNS  = list of (col fr fg fb br bg bb bold) style-change markers;
        a run extends to the next marker's col.  bg -1 = none.
Gotcha, hard-won: the cell grid is written in emission order (buffer lines, then modeline at row rows-2, then echo at rows-1) and every cell carries its own (row col). The encoder must scatter cells by their stored coordinates, not assume row-major position — an early version assumed position order and painted the modeline on row 0.

The desktop widget wire

node→wire serializes a layout tree to plain data; a handler closure is replaced by an :action id (the daemon keeps the closure keyed by id; the app sends the id back on interaction). wire→node rebuilds it on the far side. A slider click maps to a value via the node's arranged pixel width and is sent as the action's arg. See Wire codec.

6The editor

The editor is a tenant of the daemon, not a separate program. Buffers, editing, modes, keymaps, tree-sitter and rendering all live daemon-side; the editor app is a thin GTK painter.

Editor sessions

Each attached :editor app gets a session: a client, a scratch buffer (lisp-mode), a window, a renderer, and its own dedicated thread.

  • Input on the session thread. A command that reads the buffer synchronously blocks only that thread; the buffer's reply comes from a free pool worker. No pool starvation, no ask timeouts.
  • Frames are coalesced. A pusher actor subscribed to the buffer marks the session dirty with the latest snapshot; the session thread renders that one. A burst of keystrokes collapses to the latest frame.
  • Render only when needed: on a fresh buffer snapshot (typing/motion), and on input only when the minibuffer is active — M-x/completing-read change client state, not the buffer.

Modes & keymaps

Major/minor modes carry keymaps, indicators and a tree-sitter language. Dispatch walks the active keymaps for the pressed key; editing commands run in the session with *client* bound. install-editor-sessions replicates, per session, what a global start-editor would set (minibuffer handler, terminal handler, debug surface, variables) — the daemon never calls start-editor.

Rendering

render-buffer-to-frame lays the buffer into a fixed cell grid (visible lines + modeline + echo), then frame→rows encodes it. The app paints one show-text per run (not per cell) via the cell-grid painters in pine.surface.

7Tree-sitter incremental

Highlighting is real incremental tree-sitter, owned per buffer — never a re-parse from scratch, never shipped over the wire.

  • Each buffer holds a parse-state (parser · language · tree · text). An edit runs ts_tree_edit then re-parses against the old tree, so only the changed region is re-walked.
  • The byte↔char boundary is handled explicitly (TSInputEdit/TSPoint, UTF-8 aware), so multibyte edits map to correct tree points.
  • Highlighting is viewport-scoped: the request covers the visible line range plus a ~12-line margin (base = scroll-top, n = window height), not the whole file. Captures come back offset to buffer lines and are attached to the snapshot.
  • The same parse state answers structural motion (forward/backward-sexp, defun bounds).

8The desktop

The desktop is a faithful re-implementation of the author's eww setup — the bar, the echo strip, and five toggled panels — but built inside pine: the widgets, the data feeders, and the interactions are all daemon-side Lisp. There is no external broker, no yuck, no SCSS; the wire carries a declarative tree and the app renders it with GTK4.

daemon (pine.desktop) app (pine.desktop-app) build node tree ──node→wire──▶ plain data ──▶ wire→GTK build-widget (bar / 5 panels) (:widgets …) (GtkCenterBox, GtkBox, reactive cells GtkButton, GtkScale, data sources ─▶ cells GtkCalendar, cairo ring) ▲ │ └────────── (:widget-action :id N) ◀─────────────────┘ click / slider / hover

Layout engine pine.layout

A widget tree is laid out in three passes over a cell raster, giving a real box model (alignment, expansion, 2-D placement) that a linear emit model cannot:

measure  node → natural (w h)          ; bottom-up
arrange  assign absolute rects         ; top-down, slack to expanders
paint    write styled cells into rect  ; faces cascade as fg + bg fill

Nodes are CLOS objects (text-node, vstack/hstack, box, center, centerbox, scroll, action, selectable, slider, ring, calendar, picture, grid, …). A terse constructor DSL reads like markup and mirrors eww:

(centerbox :orient :v :class "bar"
  :start  (column …)          ; top    — pinned to the top edge
  :center (column …)          ; middle — floats in the slack
  :end    (column …))         ; bottom — pinned to the bottom edge

After arrange every node has an absolute rect, so hit-testing (which action / slider / row is under a point) is exact.

Wire codec

node→wire emits (TYPE PLIST . CHILDREN); every non-default style prop is in the plist, and any handler closure becomes an :action id via a callback the producer supplies. wire→node rebuilds the tree on the app side and, given an id, hands back a handler that sends that id home. Only plain data crosses.

Reactive cells

A cell holds a value and a subscriber list; setting it notifies subscribers only on a real change. A view renders inside a tracking context, so any cell read during a build records a dependency automatically — a widget just reads a cell and re-renders when it changes, no manual wiring. The bar is a live view; panels re-render while open.

Data sources the eww broker, in-image

pine.source is pine's answer to eww's babashka broker. A source is a stream (a subprocess line-stream that triggers a refresh, event-driven) or a poll (a refresh on an interval); either way the blocking IO runs on the source's own dedicated thread and writes reactive cells. Declared with defsource/defpoll, started together.

Interactions (select!/act! for wifi, sink switching, volume/brightness, media transport) are in-process closures the panel rows call — pine's replacement for eww's nREPL callbacks. Pine computes its own cpu/ram/disk, so it is more self-contained than the eww broker, which relied on eww's built-in magic vars.

Surfaces & session

The daemon hosts named surfaces — "bar", "echo", and the panels calendar/audio/network/media/ctl. defsurface NAME BUILDER registers a builder (client → node tree). push-surface builds the tree, serializes it with fresh ids (dropping the surface's stale ones), and pushes (:widgets :surface NAME :tree DATA). A tray icon calls show-panel, which pushes the panel tree then (:panel :name NAME :show t), closing any other open panel. Because the app's GTK surfaces may not exist at attach time, the app re-sends (:refresh) until the bar has content.

The desktop app

pine.desktop-app turns wire trees into GTK4 widgets and hosts them on layer-shell surfaces. build-widget maps each wire node to a real widget — GtkCenterBox, GtkBox, GtkButton, GtkScale, GtkCalendar, GtkPicture, a GtkScrolledWindow viewport — and the control-panel rings are drawn in cairo on a GtkDrawingArea with the glyph overlaid. Layer-shell (a hand-bound CFFI wrapper) anchors the bar full-height on the left, the echo as a bottom strip, and the panels on the overlay layer, all under the gtk-layer-shell namespace so the compositor's blur rule applies. Styling is GTK CSS, generated from the theme (next section); cairo is used only for the ring and the editor's cell grid.

9Theme system

One theme drives colour, metrics and faces. It lives in pine.buffer (the face layer) and is consumed by both the terminal render path (as faces → cell colours) and the desktop (as roles/metrics → GTK CSS).

(deftheme ef-dream
  :palette (bg "#232025"  fg "#efd5c5"  accent "#675072" … shadow "#0a0a10")
  :metrics (radius 8  border 2  opacity 0.4  font "Maple Mono NF")
  :faces   ((:default :fg fg) … (:ring-cpu :fg red) (:ring-track :fg bg-active) …))
  • Palette — named colour roles ((color :accent) → hex).
  • Metrics — layout constants ((metric :radius), :opacity, :font). Nothing in the stylesheet is hardcoded; radius, glass opacity and font all flow from here.
  • Faces — fg/bg/attrs, used both for terminal cell colours and for the desktop's cairo-drawn ring (which reads dedicated :ring-* faces, decoupled from syntax faces).

Generating GTK CSS

The desktop app authors CSS in Lisp: a rules list of (SELECTOR (:prop val …)) is flattened to a GTK stylesheet. glass renders a role at the theme opacity (rgba(r,g,b,0.4)); a global * reset strips GTK4's default chrome (the eww all: unset equivalent), then each rule adds back only what it wants. The result mirrors the eww stylesheet role-for-role, but derived from the theme.

10Agents, eval & supervision

Computation is first-class and isolated. This is the OTP half of pine.

Eval engine

Every evaluation runs on its own thread and captures its restarts and blocks. A surface (*on-debug*) chooses a restart by name or aborts. Evaluations are listable and addressable (list-evaluations, pick-restart, abort-evaluation) — a runaway loop is aborted without touching anything else.

Agents

An agent is :local (an in-image actor) or :process (spawn-agent starts a real SBCL that loads :pine, calls pine.agent:connect, enables remoting and registers back). Agents run remote eval/compile/run and are reached by cached ref — never by a blocking name lookup.

Cross-image debugger

A process agent points *on-debug* at the daemon: on an error it ships its restart list home to /user/agent-debug; the master picks a name and sends (:resume :eval-id N :restart NAME); the agent invokes it locally. An error in another image debugs in the editor you author from.

Jobs & supervision

list-jobs aggregates local evaluations and agent-reported work. start-agent-supervisor pings supervised process agents on an interval and respawns a dead one. Live redefinition works across images: redefine a function in the daemon and the running agent sees the new definition.

11Terminal emulator :pine/vt

A self-contained terminal emulator plus a native pty, its own ASDF system with only a CFFI dependency. It parses the VT stream into a cell grid (SGR, colours, ops) and exposes it as text, so a pine buffer can host a real terminal. It is independent of the editor and the desktop — a library the daemon draws on when a buffer needs a terminal.

As a service (replacing eww)

The daemon runs as a Guix-Home shepherd service (home-pine, parallel to the old home-eww-broker): a respawning forkexec of the same guix shell … sbcl … (pine:run-daemon) command. The desktop app is a niri spawn-at-startup, in-session so it has the wayland display — mirroring how eww split its broker (service) from its GUI (startup). Because a shepherd service starts outside the session, run-daemon discovers WAYLAND_DISPLAY and NIRI_SOCKET from XDG_RUNTIME_DIR so its sources and app-launches reach the running session — the same problem the eww broker solved. Switching bfh's home is one line: swap the service, point the desktop's bar at pine. Nothing is deleted; eww stays a fallback.

14Design principles

  • One owner of state. The daemon holds every live object. Apps hold pictures, agents hold transients. State never lives in two places.
  • Plain data on the wire. Only keywords, strings, numbers, lists, vectors cross. fset/CLOS are rendered to data at the edge.
  • Never block the shared pool or the GTK thread. Blocking IO (nmcli/pactl), synchronous buffer reads, and widget handlers each get a dedicated thread. Cross-wire talk is async tell with cached refs — never a blocking ask.
  • Compose, don't switch. Sub-techniques dispatch from real state; no mode flags choosing between alternatives, no plugin loaders. The engine/game seam is code layout + install-hooks, not a runtime PLUGIN=.
  • Faithful ports, derived from source. The desktop matches eww role-for-role and metric-for-metric, but the values come from the theme; the reference is a constraint, not a template.
  • No package-abbreviation prefixes on internal symbols. In pine.desktop it is card, not dcard; on-click, not da-click.

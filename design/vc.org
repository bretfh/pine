#+TITLE: pine: version control, git-honest
#+AUTHOR: Bret Horne
#+OPTIONS: toc:2 num:t

* Why this document exists

An editor that knows nothing about version control is blind to the one
piece of project state every working session touches. The questions are
fixed: what branch am I on, what did I change, who wrote this line,
what happened in history, and stage/commit without leaving the editor.
This document prescribes how pine answers them, and -- because this is
the corner where a famous prior-art mistake lives -- it is explicit
about what it refuses.

* What we take from prior art, and what we do not

Emacs's vc-mode made the backend abstraction the product: one command
set dispatching over RCS, CVS, SVN, git, hg, so every backend got the
intersection of all of them. git users left for magit, which won by
being git-deep -- staging hunks, rewriting history, speaking git's real
model instead of a lowest common denominator. The lesson is not "never
abstract"; it is that the abstraction must not be designed before the
second consumer exists, and must never cost the first consumer its
depth.

pine's generic layer is therefore its EXISTING primitives, not a vc
dispatch layer. Branch and dirty state are refs feeding modeline
segments and any desktop widget that cares. Hunks and blame are region
properties (properties.org). Status and log are layout buffers with
actions, like every tool. Operations are commands. A VCS backend is a
PRODUCER of those, nothing more. git is the first producer and is built
git-deep; a second VCS, if one ever matters, is another producer -- and
only then does any shared shape get named.

Refused: parsing porcelain text output (git's own interchange format is
libgit2's structs, not columns of characters), reimplementing plumbing
in Lisp, and any command named vc-anything.

* The backend: libgit2 in a process agent

The git work runs in a supervised process agent (pine.actor: spawn,
supervise-agent, the debug hook that ships an agent's conditions home
by name), speaking libgit2 through CFFI. This is the architecture using
itself: risky FFI lives where a segfault means the supervisor respawns
one agent, not where it kills the daemon holding every buffer. The
crash claim stays structural.

Ordering, per the packaging rule: libgit2 enters through guix first
(it is already packaged upstream; the manifest grows one line), the
CFFI bindings live in the agent's own code, and nothing links libgit2
into the daemon or frontend images.

Everything crosses remoting as plain readable data:

  status   ((PATH :state :modified|:staged|:untracked|:conflicted) ...)
  branch   (:branch NAME :ahead N :behind N :dirty BOOL)
  hunks    per file: ((:from L :to L :kind :add|:delete|:change) ...)
  blame    per file: ((LINE COMMIT AUTHOR TIME SUMMARY) ...)
  log      ((COMMIT AUTHOR TIME SUMMARY) ...), paged by ask args

Writes (stage, unstage, commit, checkout) are agent asks with the same
data discipline. The agent watches nothing; every answer is computed on
ask, and the editor asks on the events it already has (save, focus,
tool-buffer refresh).

* Surfaces

- Modeline: a branch segment fed by a ref the editor updates on save
  and buffer switch (defref :vc-branch; the modeline row reads it like
  any source). Dirty marker beside it.
- Hunk indicators: after save (and on find-file), the agent's hunks for
  the buffer's file become :until-edit properties with hunk classes;
  the stylesheet decides how a changed region looks. next-hunk /
  prev-hunk commands walk them via (ask BUF :properties :class).
- Blame: a command propertizing every line :sticky with commit data;
  point entering a line echoes author/time/summary from the property
  payload (the :properties :at query). A second invocation clears.
- Status buffer: show-layout rows over the status data -- Return
  visits the file, s/u stage and unstage via agent asks, c opens the
  commit prompt (prompt with :history :commits) and commits. The rows
  refresh from a fresh ask after every action; no cached model to
  drift.
- Log buffer: show-layout over log data, Return shows the commit's
  diff in a diff buffer whose regions are, again, properties.

* Ties

- project.org: repo root discovery and project root discovery are the
  same walk; the agent is also the project file-set producer.
- properties.org: hunks, blame, and diff views are consumers; vc adds
  no display mechanism of its own.
- store: commit message history under :commits; per-repo state under
  (:project ROOT ...) keys.

* Open questions

- Whether the agent holds one libgit2 repository handle per root for
  its lifetime or opens per ask; libgit2 handles are cheap to open and
  the stateless shape survives agent respawn better. Measure before
  caching.
- Interactive rebase and the rest of history rewriting: deliberately
  uncharted until the status/commit loop is daily-driven. The refusals
  above still apply when it comes.

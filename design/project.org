#+TITLE: pine: project awareness
#+AUTHOR: Bret Horne
#+OPTIONS: toc:2 num:t

* Why this document exists

pine currently has no notion of "this codebase". find-file completes
over the filesystem from the buffer's directory; M-. asks the image
about a symbol with no idea which system it belongs to; search is
whatever you type into a shell. Meanwhile two charted systems -- vc and
intelligence -- both need the same three answers before they can start:
where does this buffer's codebase begin, which files are in it, and
(for Lisp) which ASDF system does it constitute. This document
prescribes the layer that answers them.

* What we take from prior art, and what we do not

Emacs's project.el got the shape right eventually: a project is
discovered from a buffer, not configured; the VCS root is the answer
almost every time; the file list respects the VCS's ignore rules. We
take all three. What we refuse: a project file format of pine's own
(.pine-project or equivalent -- the repo already states its own
boundary), a registry of "known projects" the user maintains (the
store's recent files already say what you work on), and eagerly
indexing anything (every answer below is computed on ask, cached only
as an optimization with the git agent's help).

* The model

A project is derived from a buffer, on demand:

  root     the enclosing git worktree root when there is one, else the
           nearest ancestor holding a marker (*.asd, Makefile,
           manifest.scm), else the buffer's directory
  files    the tracked + untracked-but-not-ignored set under the root;
           when the root is a git repo the git agent answers this (it
           is a status walk libgit2 does natively), else a filesystem
           walk
  system   for Lisp buffers: the ASDF system whose source tree covers
           the file, found by scanning the root's .asd files in the
           running image (asdf:registered-systems and
           asdf:system-source-directory -- the daemon can simply ask
           ASDF, it is a Lisp image)

Nothing is stored as configuration. Per-project STATE (not config)
lives under store keys (:project ROOT ...) -- e.g. the last search, a
per-project file history -- following the persistence conventions in
pine-user.org.

* The verbs

A :project ask target beside :server and :client (buffer/buffer.lisp
dispatch, documented in api.org):

  (ask :project :root)              root for the current buffer
  (ask :project :files)             the file set, relative namestrings
  (ask :project :system)            ASDF system name or nil
  (ask :project :describe)          the verb list, as everywhere

The target resolves through the current buffer's :pathname local; a
pathless buffer (scratch) answers with the daemon's working directory
root so the verbs never error into a tool that just wants a default.

* Surfaces

- project-find-file: completing-read over (ask :project :files) with
  :history :files, bound beside find-file. This is the command that
  makes the file set worth computing.
- project-search: a query through pine.jobs running rg at the root,
  results into a layout buffer of hits (file:line + match text), Return
  jumps via find-file + move-point, the match region propertized in the
  target buffer (properties.org). The hits buffer is show-layout like
  every tool.
- load-system / test-system: for Lisp projects, (asdf:load-system
  (ask :project :system)) through the one eval path, so compiler
  conditions land in the debugger and, once intelligence.org is real,
  compiler notes land as diagnostics properties.
- The modeline's buffer segment gains nothing here; the project name is
  the vc branch segment's job (vc.org) since root and repo coincide in
  practice.

* Ties

- vc.org: the git agent is the file-set producer when the root is a
  repo; root discovery and repo discovery are the same walk.
- intelligence.org: :definition and :references scope their fallback
  (tree-sitter) searches to (ask :project :files); the image producer
  uses :system to answer "jump into this system's other files" instead
  of guessing from the package.
- store: recent-files and save-place remain global; anything
  project-scoped keys under (:project ROOT ...).

* Open questions

- Whether :files answers namestrings or (namestring . plist) once vc
  wants per-file status in the same walk; the git agent returns both
  cheaply, so the verb's shape follows its first two consumers.
- Whether system mapping should read .asd files not yet loaded into
  the image (asdf:find-system by name from the root) or only report
  loaded systems; leaning loaded-plus-findable, since load-system is
  right there.

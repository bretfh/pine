#+TITLE: pine: the point
#+AUTHOR: Bret Horne
#+OPTIONS: toc:2 num:t

* The one idea

Pine is the Lisp Machine you cannot crash and can distribute. That is the whole
thing, and every system in it exists to hold that one sentence true.

The Lisp Machine, Genera on the Symbolics, was a multiprocessing timeshared
operating system that lived in one Lisp image. It ran dozens of processes at
once under a scheduler, and its reputation, the thing people who used one never
forgot, was that errors did not kill the machine. An unbound variable or a type
error dropped that one process into the Debugger while everything else kept
running, and you inspected the frames, patched a definition, chose a restart,
and continued live. The environment was written in Lisp all the way down: the
editor, the network, the file system, the window system were one live
redefinable world you inhabited and changed from inside while it ran.

So the error model was never the flaw. It is the ideal. What the Lisp Machine
actually lacked is a different axis. Everything shared one address space on one
machine. There was no hard boundary between processes: no protected memory, so a
wild write or a runaway allocation could corrupt or exhaust the single image and
take everyone down with it, and no notion of a computation living in its own
protected process that could die alone. And it was your personal world, one
machine. The soft, logical isolation of processes in one image it had in full.
The hard, physical isolation of separate images, and distribution across
machines, it did not.

Emacs is the part of this lineage that regressed. It kept the one idea that
matters, a single malleable Lisp you live in and extend from inside while it
runs, and dropped the multiprocessing the Lisp Machine had. It is one thread, so
a blocking or looping bit of elisp freezes the whole world, and it is one
process, so there is nowhere for a dangerous computation to go. Pine wears the
emacs daemon shape, but its real ancestor is the Lisp Machine, and its move is
two-part: restore the true concurrency emacs threw away, then add the one thing
the Lisp Machine never had, a hard crash boundary you can put between images and
stretch across machines, without losing the single live redefinable world or the
debugger that comes home to you.

* Immutable data is the seam

The hard boundary would normally cost you the shared world. It does not, and the
reason is fset. An immutable value is safe to share by reference inside one
image, which is the live shared world you already had on a Lisp Machine, and
safe to serialize across a wire, which is the boundary you did not. One data
model, two transports. In one image you pass the object; at the edge you render
it to plain lists and rebuild it on the far side. Buffer snapshots, reactive
cells, declarative interface trees are all immutable values, so the same value is
the thing you inspect live and the thing that crosses the wire, and a
computation can fail hard in its own image without touching yours. This is the
piece Genera could not have, because it had no wire and no second image to send
to, and it is the piece that lets pine keep the Lisp Machine feel above a real
process boundary below.

* The daemon is the substrate

One long-lived headless SBCL process is the substrate. It owns the live state:
buffers as actors over immutable snapshots, the registries, the tree-sitter
runtime, the eval engine. It runs computations. And it never draws. That "never
draws" is discipline, not omission: the core cannot reach for a font or a pixel,
so the boundary between state and presentation stays honest and an app can be a
cell grid, a cairo surface, a tty, or a GPU without the core knowing.

Durability is not a database. No save-lisp-and-die, no event log, no snapshot to
disk. Durability is that the process stays up. While it lives nothing is lost;
restart it and you start fresh. State lives in the running image; persistence
here is liveness, not storage. Kill every app and the daemon keeps running; kill
the daemon and the apps detach. It is the tmux and emacs-daemon shape, but the
thing being kept alive is a whole parallel Lisp world, not one thread.

* Apps attach, they do not embed

An app is a separate operating-system process that brings its own surface and
its own renderer. The editor blits a cell grid through GTK; the desktop paints
cairo through the wayland layer shell. They attach over remoting: an app spins up
a client actor inside the daemon's actor-system and holds a reference back to its
own display.

The rule underneath is that the daemon ships data, never pixels. The daemon, or
an agent, builds a declarative view: a styled cell grid, a widget tree of
column, row, label, meter, with no coordinates and no fonts. It ships that value.
The app measures, arranges, and paints it locally with its own metrics and its
own backend. So the cell grid and the widget tree are the wire format between
"some image builds the view" and "some surface paints it," and fonts, cairo, and
GTK live only in the app. Because only immutable values cross, and every message
is a tag with a keyword plist that an unknown receiver drops rather than errors
on, an app can hang, spin, or segfault and the rest never feels it. The freeze
where a desktop click stalled the editor was possible only because they were
jammed into one process. Split them across the wire and it is structurally
impossible.

* The editor is the helm

The editor is not just one of the apps. It is the authoring surface and the
single debugger for the entire substrate. You write daemon logic, an agent, or
another app's interface from an editor buffer and a REPL.

And this is the heart of it. When anything anywhere errors, in the desktop, in an
agent, in the daemon itself, the live restarts stay in the image where they are
live, on the very thread that is blocked holding them, because that is the only
place they mean anything. What crosses to the editor is data: the condition
rendered to text and the restart list by name. The editor shows the menu, you
pick a name, and the editor tells that far image to invoke the restart of that
name locally, inside the extent where it is still live. You move the decision,
not the handler. One debugger surface over many images. This is deliberately the
Lisp Machine Debugger generalized across the new boundary: on one machine the
restarts were simply there in the process that erred and you chose one, and pine
keeps exactly that, as the same code with one remoting hop inserted, so the
property you loved on a single machine is preserved and not reinvented across a
network of them.

* One eval path, and agents

Every unit of running code is an evaluation on its own thread. It can loop or
block forever and only that thread is stuck. It yields one uniform object: form,
package, status, values, captured output, and on failure the condition, the
restarts as data, and the backtrace. An error does not fall to a console
debugger; the worker captures the restarts and blocks, and the helm picks one.

There is one eval path. The editor's C-x C-e, the REPL, eval-buffer, a desktop
widget's click handler, an agent's job are all the same call: run this in that
agent. The editor never calls eval directly, so the target is swappable at the
call site. An agent is where code runs: local shares this heap, process is an
isolated SBCL image with its own crash radius reached over remoting, remote is on
another host. Same call, different blast radius. A computation that might eat all
memory or segfault runs in a process agent, and the supervisor brings it back
when it dies. That is what the serialization cost buys: an isolated computation
fails hard and the editor never notices, beyond a restart menu it can ignore.

* The registry brokers capabilities

An app does not reinvent tools; it asks the registry and gets a handle. Give me
buffer scratch. Give me the audio stream. Give me an eval agent. Give me a
layer-shell surface. The registry returns a reference that speaks a known
protocol. A buffer, a data source, a language server, a model, and the parser all
sit in the registry on the same footing, addressed the same way, so external-ness
is only an implementation detail: an adapter wrapping a subprocess is just a
process agent whose messages happen to speak some protocol. The registry is also
the supervisor and scheduler: it knows every service and agent by name, watches
them, and restarts them per policy when they die. The core brokers and supervises
who does the work; it does not do the work.

* The liveness contract

One rule the whole thing exists to keep. No shared thread ever blocks, not the
daemon pool, not an app's interface thread; anything that can block or crash gets
its own thread or its own process. Every eval is its own thread; a hung eval
strands one thread, a crashed process agent strands one process, and the
supervisor restarts it. Apps are processes; one dies without touching another.
Errors come home; any image's error surfaces its restart menu in the editor, by
name, and is driven from there. And within an image you redefine live.

Data sources make this concrete. A source of workspaces, volume, or network is an
agent, registered and supervised, running its blocking subprocess IO in its own
context, never on a shared pool, publishing into a reactive cell that any app can
subscribe to. The old freeze was a source doing blocking IO on a shared pool. In
the real shape that is impossible.

* Redefine live: the goal, and the honest limit

The ambition is to redefine anything at runtime and have it take effect live:
daemon logic, an agent, an app's interface tree. Within one image this is
ordinary Lisp. Recompile a function and live callers pick it up; redefine a class
and existing instances migrate; state is immutable values you replace, not a heap
you mutate, so a swap is clean. Across images it is the hard part and it is not
fully solved. Redefining a function in one image does not change another's; to
redefine live across the substrate you ship the new definition to the target and
compile it there, over the same run-this-in-that-agent path, and the next tree
that image builds uses it. The open questions are the source of truth, where a
widget's code lives when several images run it, how instance and state migrate
across the wire, and what a live redefinition means to an app caught mid-render.
This frontier is the point, not a footnote.

* What pine enables

Pine is the Lisp Machine as your whole computing environment again: the editor,
the desktop shell with its bars and panels, the data feeds, and arbitrary long
computations all one live redefinable Lisp you author from inside, in real Common
Lisp with native threads and the real compiler and the condition system, which is
the environment the Lisp Machine was and emacs only gestured at.

The addition over Genera is not liveness and not a better debugger; it already
had both. The addition is that this live world now has hard isolation and can
span processes and machines. You can redefine anything while it runs and let
nothing you run be able to take the world down, and you can spread it across
images that fail independently and come home to one place to be debugged. It is
the Lisp Machine you could not crash and could distribute, which is the one the
hardware era never got to build.

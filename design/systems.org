#+TITLE: pine: the next systems
#+AUTHOR: Bret Horne
#+OPTIONS: toc:2 num:t

* Why this document exists

The core is built and tested: the daemon holds every buffer as an actor
over fset state; frontends are separate processes over remoting; agents
are SBCL images whose errors reach the editor's debugger; one layout
language renders buffer windows and layer-shell surfaces through one
arranger; style rules reach every attached image; and the store/world
pair restores buffers, splits, histories, and the kill ring across
restarts.

What remains is the surface: the accumulated editing commands of the
predecessors, and a small set of systems that determine whether pine
becomes a daily working environment. This document names those
systems, fixes their build order, and points to the document that
specifies each.

* The standing rule

Each system below is built from verbs on buffers, modes, commands, and
tool buffers -- primitives that already exist. None of them modifies
the core. A design that appears to require a new kind of state, a new
global variable, or a second copy of an existing mechanism should be
reworked in terms of the existing primitive.

The editing long tail -- incremental search, query-replace, registers,
rectangles, keyboard macros -- is not a system in this chart. These
are individual commands on the buffer verb protocol. Each is small,
none requires a design document, and they are added as they are
needed.

* The order

1. properties.org -- region properties. The substrate for the rest.
   Diagnostic ranges, search highlights, blame annotations, and VC
   hunk markers are all the same shape: data attached to a region of
   a buffer, adjusted or removed as the buffer is edited. Today pine
   has face runs (:set-highlights) and line overlays (:overlay); both
   become instances of one region mechanism stored in buffer state.

2. project.org -- project awareness. Which codebase a buffer belongs
   to: the root directory, the file set, and for Lisp the ASDF
   system. Version control and intelligence both depend on these
   answers, and most of them can be computed from the git repository.

3. vc.org -- version control. libgit2 in a supervised process agent;
   status, hunks, blame, and log cross remoting as data; the visible
   surfaces are built from refs, region properties, and layout
   buffers. There is no backend abstraction layer.

4. intelligence.org -- definitions, references, completion, and
   diagnostics as buffer verbs with registered producers. For Lisp
   the producer is the running image, including agent images over
   remoting; tree-sitter is the syntactic producer for other
   languages. An LSP client, if one is ever needed, is a further
   producer behind the same verbs.

5. help.org -- self-documentation. The :describe convention extended
   to describe commands, variables, keys, and modes, plus apropos
   over all registries, with every answer computed from the running
   system.

vc and intelligence are independent of each other; either can be built
first once project exists. help grows with each system whose
registries it can describe, so its groundwork can start at any point.

6. wm.org -- window management, on a parallel track. river 0.4
   separates the Wayland compositor from the window manager and
   delegates all policy to an external client over a stable protocol.
   pine is already a Wayland client in Lisp, so window management
   policy joins the system: os-window leaves arranged by the same
   layout trees and commands as editor windows, in a supervised wm
   frontend, with the compositor surviving its crashes. Independent
   of the editor-side order above.

* Refusals

Each document also states what its system deliberately omits, and
those statements are part of the specification: properties omits
per-region keymaps and priorities; project omits a project file
format; vc omits a multi-backend abstraction and porcelain parsing;
intelligence omits LSP as the protocol shape; help omits hand-written
text wherever a registry can answer. The reasoning appears in each
document.

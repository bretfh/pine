#+AUTHOR: Bret Horne

* Why this document exists

Intelligence here means the editor answering questions about code:
where a name is defined, who uses it, what completes at point, what
the compiler found wrong, what arguments a function takes. pine has
pieces -- arglist and complete-symbol against the image (editor.lisp),
tree-sitter structural motion and indentation, an eval path whose
conditions reach the debugger -- but no protocol connecting them, so
M-. sees only the symbol under point and no query knows which files
belong to the codebase. This document specifies the protocol, its two
producers, and pine's position on LSP.

* The claim

For Lisp, the running image already holds what a language server
would compute. Definitions, callers, arglists, and documentation of
everything loaded are runtime facts SBCL indexes (sb-introspect:
find-definition-sources, who-calls, function-lambda-list); the
compiler reports conditions with source locations; macroexpansion is
an eval away. An external analyzer cannot know more about the image
than the image does.

Because pine's eval path targets any image (*eval-target*: the
daemon, or any agent over remoting), every verb answered by the image
is answered by whichever image is being driven. A definition inside a
running agent's image, or the callers of a function in the frontend's
image, resolve through the same remoting hop the debugger already
uses. This is a capability the single-image predecessors do not have.

LSP is therefore not the shape of this system. It is one possible
producer, discussed in its own section below.

* The verbs

Buffer asks, with producers registered per mode (documented in
api.org):

  (ask BUF :definition [:of SYMBOL])   -> ((FILE LINE COL KIND) ...)
  (ask BUF :references [:of SYMBOL])   -> same shape
  (ask BUF :complete PREFIX)           -> candidates, in the existing
                                          completion machinery's shape
  (ask BUF :arglist [:of SYMBOL])      -> string (exists; moves here)
  (ask BUF :hover [:at (L . C)])       -> string, or nil
  (ask BUF :diagnostics)               -> the buffer's diagnostic
                                          properties, as data

A producer is a function registered for a mode keyword and a verb,
following the register-and-dispatch shape the completion sources
already use (register-source, editor.lisp). Producers answer in
registration order: for point queries (:definition, :hover) the first
non-nil answer wins; for set queries (:references, :complete) the
answers are merged. With two producers no ranking system is needed;
one is not added in anticipation.

* Producer one: the running image

- :definition and :references from sb-introspect against the target
  image, package-aware through the buffer's :package local. Source
  locations map to (FILE LINE COL); files open through find-file, so
  save-place and project scoping apply.
- :complete from the package system -- what complete-symbol does
  today, registered as a producer.
- :hover combines documentation and arglist for the echo area.
- :diagnostics from compilation: load-file, eval-buffer, and
  load-system capture compiler conditions together with their source
  ranges and write them as :until-edit properties (properties.org)
  with the condition text as payload. Errors keep their existing path
  into the debugger; notes and warnings additionally become visible
  in the buffer.

All image queries honor *eval-target*.

* Producer two: tree-sitter

For languages with a grammar and no image to ask: definitions and
references resolved syntactically. The tree already held in buffer
meta answers in-buffer queries; project-wide queries parse across
(ask :project :files) filtered by extension, running under pine.jobs
so the session does not block. Syntactic answers are labeled as such
in result buffers: a tree-sitter :references answer means occurrences
of the same identifier, not call sites. This producer gives M-. and
M-? useful behavior in every language with a grammar as soon as the
protocol exists.

* Surfaces

- M-. sends (ask BUF :definition); one result jumps directly; several
  open the xref layout buffer -- show-layout rows, Return jumps, the
  visited region briefly propertized. M-, pops the jump ring, which
  is a store list and so survives restarts.
- M-? sends :references into the same buffer shape.
- Completion, the arglist echo, and the eval flows keep their
  commands; their internals become registered producers, so a new
  mode gets all of them by registration rather than by special cases.

* LSP

If a language without an image comes to need semantic answers that
syntax cannot provide -- types, rename, cross-file references -- an
LSP client can be added as a third producer behind the same verbs. An
LSP server process is a natural fit for a pine process agent: spawned,
supervised, its failures surfaced in the editor while the daemon runs
on. Nothing in the verbs, surfaces, or existing producers would
change. No LSP work is specified in this document.

* Omitted

- LSP as the protocol shape. The verbs are derived from what the
  surfaces ask, not from another system's wire format, capability
  negotiation, or position encoding.
- Per-language analyzers in the daemon. Anything heavier than
  tree-sitter parsing runs in a job or an agent.
- Surfaces that bypass the verbs. Once the protocol exists, no
  command reaches into sb-introspect or the tree-sitter tree
  directly; the verb layer is what keeps producers replaceable.

* Open questions

- Whether the image's :references should include who-macroexpands and
  who-binds alongside who-calls, or expose a :kind filter. The first
  real use decides.
- The jump ring's depth, and whether it is global or per-project;
  either is a single store key.

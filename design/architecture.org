#+TITLE: pine architecture
#+AUTHOR: Bret Horne
#+OPTIONS: toc:3 num:t

* What pine is

pine is a Lisp Machine substrate shaped like the emacs daemon.

One headless SBCL process is the substrate: a long-lived daemon that owns live,
immutable, addressable state and runs computations. It does not draw. Apps
attach to it as separate OS processes and render. Agents attach to it as
separate contexts and compute. The editor is one app, and it is the helm: the
place you author from and the place every error comes home to.

Two properties held at once:

- Within an image it is a Lisp Machine. One heap of live, addressable,
  redefinable CLOS objects and fset values you inspect and change at runtime.
  Genera and Hemlock.
- Between images it is Erlang. sento gives every actor a uniform address, so
  isolation, parallelism, and distribution come from process boundaries, not one
  fragile heap. Processes are supervised; one can crash without taking the rest
  down. OTP.

fset is the seam. An immutable value is safe to share by reference inside one
heap and safe to serialize across a wire. One data model, two transports. That
is what lets a computation fail hard in its own image without touching the
editor: the thing Genera could not do because it had no isolation, and the thing
emacs cannot do because it is one single-threaded process.

The extension language is real Common Lisp on SBCL, not Elisp: native threads,
the real compiler, the condition system, FFI. That is why pine can sit closer to
a Lisp Machine than emacs does.

* The daemon is the substrate

One headless SBCL process. One actor-system. No GTK, no cairo, no fonts, no
rendering: it cannot draw and does not try. It owns:

- buffers, as actors over immutable fset state;
- the registries: buffers, commands, modes, faces, and services/agents;
- the tree-sitter runtime;
- the eval engine.

It holds state and runs computations. That is the whole job. Kill every app and
it keeps running. Kill it and the apps detach.

Durability is that it stays up. No save-lisp-and-die, no event log, no snapshot
to disk. State lives in the running image; while the daemon lives nothing is
lost; restart it and you start fresh. It is a long-lived process, not a
database. This is the emacs --daemon shape with an actor network in place of one
thread.

* Apps attach, they do not embed

An app is a separate OS process. It brings its own surface and its own renderer.
It attaches over sento remoting: it spins up a client actor inside the daemon's
actor-system and holds a ref back to its own display process.

- the editor: a GTK window, a cell-grid renderer, keyboard and mouse input.
- the desktop: a layer-shell backing surface (the wayland desktop shell:
  bars, panels, the echo strip), a cairo renderer.

They share nothing but messages and serialized fset values. No shared thread, no
shared heap. So the desktop can hang, spin, or segfault and the editor never
feels it, and the reverse. Today everything runs in one process and that is the
central divergence to unwind: the freeze where a desktop click stalled the
editor happened only because they are jammed together. Split them and it cannot
happen.

A second editor is another attach. A remote editor is the same attach over the
network. tmux and emacs-daemon: kill the last app and the daemon keeps running;
kill the daemon and the apps detach.

* The editor is the helm

The editor is the primary app and the authoring surface. You write daemon logic,
an agent, or another app's UI from an editor buffer and a REPL. It is also the
one debugger surface for the whole substrate.

This is the part that matters: a widget you are writing runs in the desktop
app's image or an agent's image, not the editor's. When it errors, it is still
SBCL, so it has a condition and live restarts. Those restarts stay in the image
where they are live, on the thread that is blocked holding them. What crosses to
the editor is data: the condition rendered to text, and the restart list by
name. The editor shows the restart menu. You pick a name. The editor tells that
image to invoke the restart of that name, and the image, still inside the extent
where the restart is live, invokes it locally.

You move the decision, not the handler. So every error anywhere in the
substrate, in any app or agent or the daemon itself, surfaces its restart menu in
the editor you are typing in, and you drive it from there. One debugger surface,
many images. The in-image debugger and the cross-image debugger are the same
code with one remoting hop inserted.

* The registry brokers capabilities

An app does not reinvent tools; it asks the registry and gets a handle. Give me
buffer scratch. Give me the :audio stream. Give me an eval agent. Give me a
layer-shell surface. The registry returns a ref that speaks a known protocol.

That is the shared semantics: the editor and a desktop widget both drive the
layer-shell because the surface capability is one brokered thing with one
contract, not two reimplementations. A buffer, a data source, a language server,
a model, and the tree-sitter parser all sit in the registry on the same footing,
addressed the same way. External-ness is an implementation detail: an adapter
that wraps a subprocess is just a process agent whose messages happen to speak a
protocol.

The registry is also the supervisor and scheduler. It knows every service and
agent by name, watches them, and restarts them per policy when they die. The
core brokers and supervises who does the work; it does not do the work.

* Immutable data is the only thing that crosses

Everything shared is an fset value: buffer snapshots, reactive cells, declarative
UI trees. In one image you share it by reference. Across the attach wire you
serialize it: fset values render to plain lists and rebuild on the far side,
because sento will not serialize fset's internals. In-image pass the object; at
the edge serialize a stable value.

An app subscribes to the data it cares about and re-renders when it changes;
input flows back the other way as messages. Messages are (tag &rest plist). An
unknown tag warns and drops, never errors, so an actor survives a bad send from a
buggy peer. That is the robustness floor.

* The app renders, the daemon never does

The daemon ships data, never pixels. It, or an agent, produces a declarative UI
tree: a value, column / row / label / icon / meter, no coordinates, no fonts. It
ships the tree. The app measures, arranges, and paints it locally with its own
metrics and its own backend: the editor blits a cell grid, the desktop paints
cairo through the layer-shell. Fonts, cairo, GTK all live in the app, never in
the daemon.

That is why the daemon stays headless and an app could be a tty or a GPU surface
without the daemon knowing. The styled cell grid and the widget tree are wire
formats between "some image builds the view" and "the app paints it".

* Eval and agents

Every unit of running code is an evaluation on its own thread. It can loop or
block forever and only that thread is stuck. It produces one uniform object:
form, package, status, values, captured output, and on error the condition, the
restarts as data, and the backtrace. An error does not drop to a console
debugger: the worker captures the restarts and blocks, and the helm picks a
restart by name or aborts.

One eval path. The editor's C-x C-e, the repl, eval-buffer, a widget click, an
agent's job all become one call: run this in that agent. The editor never calls
eval directly, so swapping the target agent is transparent at the call site.

An agent is where code runs:

- :local   an in-image actor; shares this heap.
- :process an isolated SBCL image reached by remoting; own heap, own crash radius.
- :remote  an agent on another host.

Same call, different blast radius. A computation that might segfault or eat all
memory runs in a :process agent, and the supervisor restarts it when it dies.
That is what the serialization cost buys: an isolated computation fails hard and
the editor never notices, beyond a restart menu it can choose to ignore.

* Data sources are supervised agents

A data source (niri workspaces, pactl volume, nmcli) is an agent, registered and
supervised like any other. It runs its blocking subprocess IO in its own
isolated context, its own thread or its own process, never on a shared pool of
the daemon or an app. It publishes into a reactive cell. The desktop app
subscribes to that cell and rebuilds its widget tree.

So a source is neither the desktop's private thing nor daemon core work: the
core brokers and supervises it, the source owns its own IO, the desktop is the
primary consumer, and any app can subscribe to the same cell. The freeze was a
source doing blocking IO on a shared actor pool. In the real shape that is
impossible, because a source's IO never touches a shared thread.

* Redefine live (the goal, and the honest limits)

The ambition: redefine anything at runtime and have it take effect live. Daemon
logic, an agent, an app's UI tree.

Within one image this is ordinary Lisp. Recompile a function or method and live
callers pick it up; redefine a CLOS class and update-instance-for-redefined-class
migrates existing instances. State is immutable values you replace, not a heap
you mutate in place, so a swap is clean.

Across images it is the hard part, and it is not fully designed yet. Redefining a
function in the editor's image does not change the desktop app's image or an
agent's image; they are separate heaps. To redefine live across the substrate you
ship the new definition to the target image and compile it there, over the same
eval-in-that-agent path. That much the eval path can already carry: agent-eval a
defun into the desktop app's image and the next tree it builds uses it. The open
questions are the source of truth (where a widget's code lives when several
images run it), instance and state migration across the wire, and what a live
redefinition means for an app that is mid-render. Treat this section as intent
with a partial mechanism, not a solved problem.

* The liveness contract

The rule the whole thing exists to keep:

- No shared thread ever blocks. Not the daemon pool, not an app's UI thread.
  Anything that can block or crash gets its own thread or its own process.
- Every eval is its own thread. A hung eval strands one thread; a crashed
  :process agent strands one process; the supervisor restarts it.
- Apps are processes. An app dies without touching the daemon or another app.
- Errors come home. Any image's error surfaces its restart menu in the editor,
  by name, and is driven from there.
- Redefine live. Within an image, standard Lisp redefinition; across images, ship
  the form to the target and compile it there.

* Lineage

hemlock-port, hecl, and pine are three passes at this one substrate. Each pass
dropped a stack and kept the idea.

- hemlock-port: a Hemlock port on ECL with CLX/TTY/webui surfaces and a
  hand-rolled binary wire. Kept the actor idea, the editor / eval-server split,
  tree-sitter, the buffer model. Dropped the binary wire (to sento), ECL, CLX.
- hecl: a rebuild on ECL and LQML/QML with a mobile target. Kept the sento actor
  network, immutable fset buffers, the client / server split, the cell-grid
  surface, the agent registry, the layout node tree. Dropped QML, ECL, mobile,
  roswell.
- pine: SBCL, sento with remoting, fset, closer-mop, GTK4 and cairo, gtk4-layer-
  shell. Adds pine.eval and reactive cells.

* Status

Built and running (make dev is a typable GTK editor; make check loads clean):

- server / client split; per-session state on the client; the runtime on the
  server; typed actor messages.
- buffers: immutable fset actors, edits as messages, snapshots to subscribers,
  undo, registry.
- surface protocol with a GTK cell-grid surface and a headless test surface; the
  cell-grid wire; a UI-thread render pump.
- modes: the CLOS composition backbone (major and minor, keymap layer plus
  execute method-combination layer), precedence, transparent modes. commands as
  objects, prefix argument, argument descriptors, M-x, editor-variables,
  describe-key / bindings / mode / variables.
- tree-sitter: raw CFFI to libtree-sitter (cffi-libffi for by-value nodes, no C
  shim); commonlisp and scheme grammars from Guix; highlight via the renderer
  actor; structural motion; byte to character mapping correct under UTF-8.
- pine.vt terminal buffers: pty, reader thread, bounded drain, terminal-mode.
- pine.eval: off-thread evaluation, uniform evaluation object, restart-capable
  debugger surface in the editor. C-x C-e, eval-buffer, the repl, and desktop
  clicks route through it.
- the desktop: layer-shell surfaces on reactive cells fed by data sources; a
  <layer-shell-surface> that implements the surface protocol; sources registered
  in the service registry.

The central divergence from this document: the daemon, the editor, and the
desktop all run in one process today. The freeze that a desktop click could hang
the editor is a direct result. The real shape is three processes, attached over
remoting, with sources as isolated agents.

Designed here, not yet built:

- Split the topology: headless daemon, editor app, desktop app, each its own
  process over remoting. This is the load the rest depends on.
- The no-hang contract enforced everywhere: no shared thread blocks; sources and
  any blocking IO run isolated.
- Cross-image errors: an agent or app error surfaces its restarts in the editor
  by name; the editor drives the choice back.
- A real :process agent: spawn SBCL (drop the dead ecl path), actor-system with
  remoting, register back; supervised with death detection and restart policy.
- One eval path: all editor eval becomes eval-in-agent :local, so the target is
  swappable.
- The jobs surface: one buffer listing every live evaluation across every agent.
- Live cross-image redefinition: ship a form to a target image and compile it
  there; the state and source-of-truth questions above.

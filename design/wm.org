#+AUTHOR: Bret Horne

* Why this document exists

pine is the environment: the editor, the desktop surfaces, and the
processes behind them are one live Lisp system. Window management has
been the missing layer -- pine's editor and desktop run as clients of
a compositor whose policy pine does not control. Writing a Wayland
compositor to close that gap would mean reimplementing DRM/KMS,
input hardware, and frame scheduling, none of which is pine's
subject.

river 0.4 removes that obstacle. It splits the compositor from the
window manager: river keeps the display server and compositor roles
(input routing, buffer composition, frame-perfect rendering, outputs,
Xwayland), and delegates every policy decision to a single external
Wayland client through the stable river-window-management-v1
protocol. A window manager is an ordinary Wayland client, explicitly
workable in a garbage-collected language, and pine already is a
Wayland client in Lisp. This document specifies pine as that client:
window management policy in the daemon, expressed in the same layout
language that arranges editor windows, redefinable live from the
editor.

* The protocol, summarized

river-window-management-v1 (version 5; river does not break window
managers) divides all state into two categories and batches changes
to each into atomic sequences.

Window management state affects communication between the compositor
and windows: proposed dimensions, fullscreen, keyboard focus, close
requests, decoration mode. It may only change during a manage
sequence: the server sends all state changes since the last sequence
(new windows with title/app-id/parent/size hints, pointer
enter/leave, interactions, binding presses, output changes) followed
by manage_start; the client responds with its policy requests and
manage_finish.

Rendering state affects only compositor output: window positions and
stacking order (river_node_v1), compositor-drawn borders, clip boxes,
and the placement of the window manager's own surfaces. It applies
atomically at render_finish. The server reports the dimensions
windows actually took before render_start, so a re-tile is applied in
one frame with no gap or overlap visible.

Between sequences the window manager is idle. Typing and pointer
motion never round-trip through it, which is why an SBCL image is an
acceptable window manager where it would not be an acceptable
compositor.

Three further interfaces matter to pine:

- river_shell_surface_v1: the window manager's own UI surfaces
  (bars, menus, notification panels) live in the same render list as
  windows, positioned by the same render sequence, with
  sync_next_commit tying their content updates into the same atomic
  apply.
- river_seat_v1: focus_window / focus_shell_surface, pointer
  bindings, window_interaction events (policy-over-mechanism: the
  compositor reports that a window was clicked, the manager decides
  what that means), and interactive operations (op_start_pointer,
  cumulative op_delta events) for pointer-driven move/resize.
- river-xkb-bindings-v1: keyboard chords registered with the
  compositor; presses arrive as events during manage sequences.

Decorations are window-manager-drawn surfaces offset from windows
(river_decoration_v1), and compositor-drawn borders are available
without any surface at all (set_borders).

* What we take from prior art, and what we do not

reka (an Emacs window manager for river) validates the shape: a
protocol pump that answers manage/render sequences from mirrored
state, with policy applied asynchronously and manage_dirty raised
when policy changes. pine keeps that split. reka's other half is a
1500-line Rust dynamic module that exists because Emacs cannot speak
Wayland; pine speaks Wayland in Lisp (wayflan, src/wayland/) and does
not need it. The pump is Lisp like everything else.

From the EXWM lineage pine takes the goal -- application windows as
first-class objects of the editor's command language -- and not the
mechanism: no X11, no reparenting, no key injection into foreign
clients. Windows receive their input directly from the compositor;
pine's bindings are compositor-registered chords, not interception.

* The model

A third frontend kind beside editor and desktop: the wm app. It is a
Wayland client of river (binding river_window_manager_v1,
river-xkb-bindings-v1) and an attached pine client of the daemon over
remoting, exactly as the editor frontend is.

The daemon owns policy. Each river output holds a layout tree in the
node language: os-window leaves (a new leaf kind carrying a river
window's identifier, title, app-id) arranged by column / row / rule
with expand weights -- the same trees, the same arranger, the same
arithmetic that fits editor windows. Splits, deletes, focus cycling,
and swaps are commands dispatched through the same keymaps as every
other command; a chord registered with the compositor arrives at the
wm frontend, crosses to the daemon, and runs an ordinary command that
mutates the tree.

The wm frontend holds a mirror of the arranged state and answers
sequences from it without waiting on the daemon: a manage sequence is
answered with the proposals already computed; a render sequence
places nodes at their computed rects. When the daemon changes policy
(a command ran, a rule changed, init reloaded) it pushes the new
arrangement to the frontend, which raises manage_dirty and applies it
in the next sequences. When the compositor reports change (new
window, title change, interaction, output change) the frontend
forwards it to the daemon and answers the current sequence from the
state it has; the daemon's response arrives as a later dirty cycle.
Sequences are therefore always answered promptly and policy is
always daemon-owned; the two clocks meet through manage_dirty, which
the protocol provides for exactly this.

Desktop surfaces join the render list: under river, the bar and
panels become river_shell_surface_v1 surfaces placed by the same
arranger that places windows, atomically. river also implements its
own layer-shell, so the existing desktop frontend runs unchanged
until that migration; nothing blocks on it.

Failure behavior composes. river survives window manager death and
allows a new manager to bind (hot swap is an explicit feature). The
daemon already supervises and respawns frontends. A wm frontend crash
therefore costs nothing: river keeps the session and every window,
the daemon respawns the frontend, it re-binds and re-arranges from
daemon state. A daemon restart costs no more: the world (doc/pine-user.org, The world) gains
an os-arrangement contributor, so the window trees come back like the
editor splits do.
Window management policy becomes something you can crash, patch in
the editor's debugger, and resume -- the claim philosophy.org makes
for every other part of the system, now including the desktop itself.

* The mapping

  protocol                        pine
  ------------------------------  ----------------------------------
  manage sequence                 arrange pass over the output's tree
  propose_dimensions              leaf rects from the engine arranger
  render list order               tree order
  node set_position               rects, as the editor wire carries
  shell surfaces                  desktop surfaces, same arranger
  xkb bindings                    keymap chords, same dispatch
  window_interaction              focus policy command
  op_start_pointer / op_delta     interactive move/resize commands
  window titles / app-ids         completion source (switch-window)
  hot swap / respawn              supervised frontend, world restore

* Development path

The window manager is developed without leaving the current session:
river runs nested as a window under any Wayland compositor, and the
wm frontend connects to the nested instance. Verification is by
screenshot through the nested compositor, the same eyes-first
discipline used for the editor's split work (bench/split-shot.lisp).
The sequence of first steps:

1. guix packaging: river at 0.4 or later (guix carries 0.3.12, the
   pre-split architecture; zig 0.16 is present, wlroots 0.20 is the
   dependency to package). Protocol XMLs come from the river package
   output, not vendored into pine.
2. wayflan bindings for river-window-management-v1 and
   river-xkb-bindings-v1, beside the existing layer-shell bindings
   in src/wayland/.
3. The wm frontend: bind, mirror, pump; the daemon's os-window trees
   and commands; nested-river shots proving tiles, splits, focus,
   and a binding round-trip.
4. Shell-surface migration of the desktop, input/output
   configuration (river-input-management-v1, river-libinput-config-v1,
   river-xkb-config-v1), and the os-arrangement world contributor.

* Omitted

- A compositor of pine's own. river's split makes the compositor a
  display engine pine drives; reimplementing it buys nothing.
- Key injection into foreign clients (the EXWM simulation-key
  mechanism). Windows own their input; pine's control surface is
  bindings and window management, not synthetic events.
- Animations and visual effects beyond what the protocol's atomic
  apply provides. If river grows shader hooks later, they arrive as
  rendering state like everything else.

* Open questions

- Whether os-window trees live per output only or can nest an editor
  frontend's own toplevel specially (the editor is itself a river
  window managed by this system; nothing in the protocol makes that
  circular, but the default arrangement should probably privilege
  it).
- Floating windows: the protocol places any window anywhere, so
  floating is a policy choice -- likely a float flag on the os-window
  leaf excluding it from the tree arithmetic, rendered above via
  place_top. The first interactive-move implementation decides.
- Multi-seat: the protocol models seats fully; pine's client model
  is per-seat-ready but nothing has exercised it. Deferred until a
  second seat exists in practice.

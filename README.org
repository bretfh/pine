#+TITLE: pine

Pine Is Not Emacs. Pine attempts to capture some of the spirit of emacs. If
emacs can be viewed as a text editing framework, pine trys to do so for
components of your os. Think of it as a layer on top of your host that can offer
a uniform way to interact pine through a virtual fs from other languages or ofc
from pine itself using cl. You can render anything from editors, to desktop
widgets, to managing your windows (wayland only & leveraging river's protocol).
Highly experimental and subject to change but im using it for my own needs.

[[file:doc/architecture.org][doc/architecture.org]] is what it is and how it is
put together so far.

* The shape of it

Everything is at a name in one tree, and three kinds of thing stand at a name:

: mount        serves what is under it: /dev/audio, /text/notes, /proc/edit
: value        holds what was written: /dev/audio/volume, once you have set it
: derived      is worked out from what it read, and again only when that moves

A kind of mount answers for the names under it by methods on =read= and
=write=, one per name, and =ls= lists them. Everything pine has is a class that
serves a subtree that way, and a directory on disk or another pine is mounted the
same way:

: mount                    serves a subtree
: |- job                   something that runs, at /proc/<name>
: |  |- thread, actor, program, image
: |  \- system             a package pine loaded; it starts and stops
: |- document              text, and the structure its mode gives it, at /text/<name>
: |  \- region             a span of one, with its own sub-regions
: |- device                something the machine has, at /dev/<name>
: |- surface               a widget tree and where it goes, at /ui/surface/<name>
: |- directory             a directory on this machine
: \- peer                  another pine, here or on another machine

* The protocol

Four verbs, on the tree, from inside pine, from the command line, and as a line
of json each way over a socket for anything else. A read answers now; a write
makes the place if nothing stands there; a watch says so whenever it moves; ls
lists what is under a name. Which class answers is the mount's business, so the
same four words reach a document, a running job, a device or another machine:

: ./pine read  /dev/audio/volume
: ./pine write /dev/net/wifi "cafe-guest"
: ./pine watch /dev/media/title
: ./pine ls    /proc

The same four words in cl, taking the same kind of argument, so what a config
says and what you type are one language:

#+begin_src lisp
  (read  /dev/audio/volume :else 0)   ; the value, and :held or :absent
  (write /dev/net/wifi "cafe-guest")
  (watch /dev/media/title (lambda (place said) ...))
  (ls    "/proc")
#+end_src

=./pine= with no verb lists the rest, which are all conveniences over those:
=use=, =drop=, =systems=, =jobs=, =reload=, =start=, =stop=, =restart=,
=status=, =shell=.

* What's in it

Pine is modular. Each of the ways pine provides a handle to something on your
host for usage, treesitter, host machine information, rendering with wayland,
each of these is a system, a class you start and stop at =/proc/<name>=, and
each is written in the same language as everything You load in systems with use:

: ./pine use text     # documents, modes, and the parse behind them
: ./pine use host     # the machine's own devices, at /dev
: ./pine use edit     # windows onto documents, and the chords that act on them
: ./pine use term     # programs with screens of their own, as documents
: ./pine use desk     # a bar, and the panels it opens
: ./pine use wm       # the compositor, in the namespace

What a system mounts while it starts is its, and dropping it takes that back:
its surfaces, its devices, the jobs it started, the chords it bound. What its
file defined at the top level stays defined, the way a defun does:

: ./pine drop desk

Pine is designed with niri and river in mind, but the idea is pine be unbiased
to work with an existing wm or more directly with river's protocol:

: ./pine read  /wm/windows
: ./pine write /wm/focused 3
: ./pine write /wm/layout wide      # where pine is the one laying them out
: ./pine read  /wm/placement        # and where each window ended up

A layout is a class with one =arrange= method, so a config writes its own.

* Making it yours

=~/.config/pine/init.lisp= is read into =pine/user=, a package that uses =cl=
and =pine=. An app is a package of its own that uses the same two, and takes a
system's words as it needs them: =(use-package '(#:pine/ui #:pine/mode
#:pine/host))=. The words are symbols the compiler resolved, so one misspelled
is a build that fails rather than one that quietly is not in the language.

There are six sentences to say, and each is said one way, by a config and by
pine's own bar, editor and window manager alike:

#+begin_src lisp
  (defpackage #:notes (:use #:cl #:pine))
  (in-package #:notes)

  (defclass notes (system) ())                    ; a system: at /proc/notes once used
  (defmethod start ((s notes))
    (mount (make-instance 'mount) "/notes")       ; a thing stands at a name
    (defcommand "note" (title said)               ; a command, run by name
      (:describes "write something down")
      (write (format nil "/notes/~a" title) said))
    (bind 'text "C-c n" "note")                   ; a chord, in a mode
    (defsurface sticky (:as 'overlay)             ; a surface: what to draw, where
      (label (read "/notes/today" :else ""))))

  (defclass note (prose) ())                      ; a mode: what kind of text
  (defmethod handles ((m note)) '("*.note"))      ; which files are that kind
  (defmethod regions ((m note) document) ...)     ; what its text divides into

  (defdevice vcs :describes "the checkout")       ; a device: something the machine has
  (defbacking vcs (:needs "git")                  ; one way of answering it here
    (branch :reads (sh "git rev-parse --abbrev-ref HEAD")))

  (defclass column-of-two (layout) ())            ; a way to lay windows out
  (defmethod arrange ((l column-of-two) windows area) ...)
#+end_src

A thing that serves a subtree of its own is a class under =mount=, answering
for each name under it with a method on =read= or =write=; that is how a job,
a document and a device are written, and it is the same for yours.

You can see what a config draws before you run it. =make shot= renders the frame
and every surface as PNGs, with no display and no compositor:

: make shot CONFIG=~/.config/pine/init.lisp

- [[file:examples/init.lisp][examples/init.lisp]] is a config to copy.
- [[file:examples/notes/notes.lisp][examples/notes/notes.lisp]] is a small app: a
  place at =/notes=, a mode that divides its text into headings, a role and a
  surface of its own, its own commands and a chord bound to the keyboard.
- [[file:examples/vcs/vcs.lisp][examples/vcs/vcs.lisp]] is an app that brings a
  device of its own, answered by git or by jj, whichever this machine has.

: ./pine use notes
: ./pine run note today "it works"
: ./pine read /notes
: ./pine read /notes/today
: ./pine toggle /ui/surface/sticky/shown
: ./pine drop notes                    # and everything it put there goes

* Running it

I develop pine on guix:

: git clone https://github.com/bretfh/pine
: cd pine
: make bin        # one binary: the daemon and the cli
: ./pine start    # reads ~/.config/pine/init.lisp and starts what it declares
: ./pine status

Without guix, on a linux without it or on a mac (untested), =FOREIGN=1= builds
against ocicl and your own package manager. =make foreign= says what is missing
and how to get it:

: make foreign                    # what is missing, and how to get it
: make foreign-deps FOREIGN=1     # the lisp systems, through ocicl
: make foreign-wayflan FOREIGN=1  # one patch wayflan needs
: make foreign-libs FOREIGN=1     # the tree-sitter grammars and the pty shim
: make bin FOREIGN=1

* Hacking on it

: make check       # load everything, warning free
: make test        # the suite
: make repl        # a repl with pine loaded
: make shot        # the frame and the surfaces as png, headless
: make screen      # pine on a headless compositor, and a shot of what it drew
: make screen COMPOSITOR=river         # with pine as the window manager too
: make docs        # doc/*.dot -> the png and svg beside them
: make bench WORK=typing SIZE=20000   # a workload, through the real paths
: ./pine run metrics                  # what the daemon you are using is doing
: ./pine shell     # a repl in this terminal, no daemon

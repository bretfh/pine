#+TITLE: pine: help and self-documentation
#+AUTHOR: Bret Horne
#+OPTIONS: toc:2 num:t

* Why this document exists

Emacs is learnable from inside because every question about the system
is answered by the system: any key, function, or variable can be
described, and the answer links to the source. pine has the seed of
this: every ask target answers :describe with its verb list, every
defonce carries documentation, and docstrings are maintained across
the tree. This document specifies how that seed grows into a full
help system, and the rule that keeps it accurate.

* The rule

Help is computed from the running system, not written beside it. A
help buffer is built at ask time from the registries and docstrings of
the running image. Text that could disagree with the code it describes
does not belong in the help system; the org files under doc/ and
 record intent and architecture, and the current state of any
definition is answered only by the image.

* What exists

- (ask TARGET :describe) on :server, :client, :project (specified in
  project.org), and every buffer: the verb lists.
- describe-key (%describe-key-text, editor.lisp): reports what a key
  runs, resolving across all active keymaps.
- %bindings-text and %variables-text (editor.lisp): active bindings
  and declared variables with their documentation, as plain text.
- defonce :documentation, defcommand docstrings, mode indicators, the
  server's faces and modes registries, and store keys readable from
  scratch.

* Specified

- describe-command, describe-function, describe-variable,
  describe-mode, and describe-key as layout buffers (show-layout)
  rather than echo strings: name, docstring, the bindings that reach
  it, the mode that owns it, and a source jump through the
  intelligence :definition verb. Help and intelligence share that
  seam, so help buffers gain source jumps when intelligence.org is
  built.
- apropos: one prompt matching across all registries -- commands,
  variables, modes, faces, refs, buffer verbs, store keys -- with
  results grouped by kind in a layout buffer; Return describes the
  item, M-. jumps to its source. The orderless completion engine
  provides the matching; apropos is a candidates producer over the
  registries.
- The bindings and variables listings become interactive tool
  buffers: rows, Return describes, and variables are settable in
  place through the prompt machinery and (setf (var ...)).
- The vocabulary table in api.org becomes queryable -- (ask :server
  :words) or a help command rendering it -- so the word list is
  available while writing init code.
- Each new system's registries join apropos as they are built:
  project verbs, vc commands, intelligence producers, world
  contributors.

* Omitted

- Hand-written help text wherever a registry can answer. A missing or
  wrong docstring is fixed at the definition, not papered over in the
  help system.
- A dedicated help mode with its own navigation. Help buffers are
  layout buffers with the same selection and Return behavior as every
  other tool.
- Documentation coverage tooling. The docstring discipline is
  maintained in review, not enforced by machinery.

* Open questions

- Whether describe buffers show the effective value and binding
  context (this client, this buffer's modes) or the global view with
  local differences marked. The effective view with differences
  marked is the likely answer, since the local state is usually what
  prompted the question.
- Whether apropos matches docstring bodies or names only. Names
  first; body search can be a flag later.

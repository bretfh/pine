#+TITLE: pine tree-sitter
#+AUTHOR: Bret Horne

Describes what src/ts/ actually does: index (byte offsets over the line seq),
runtime (bindings, grammars, parse state, the band, motion), parser (the
per-buffer actor) and highlight (the language walks and indentation).

* Bindings

Raw CFFI (cffi:defcfun) to libtree-sitter, in one file, no C wrapper.
tree-sitter returns TSNode (and TSQueryCapture, which embeds one) by value;
cffi-libffi handles by-value struct returns and arguments, so the shim the old
plan needed is gone. TSNode's context[4] array is flattened to four :uint32
scalars because CFFI has no by-value translation for an array member; the fields
are never read from Lisp, only passed back to ts_node_*.

libtree-sitter itself is the Guix "tree-sitter" package, loaded by name.

* Languages are declarations

A language is written at /syntax/?name: the grammar to load, what each node type
paints, and what a symbol in head position does to the form it heads. Ordinary
data, not a provider, because the tree is the storage and there is nothing
behind it -- so amending one macro is a write to one leaf:

  (write /syntax/commonlisp/head/defcmd {:rest :body :indent 2})

src/ts/lang/commonlisp.lisp, src/ts/lang/scheme.lisp and src/ts/lang/pine.lisp
are the three pine ships. pine's own is the smallest and the proof: it is
Common Lisp's declaration with a different grammar and five node rules for what
the readtable adds, not a second walker.
Adding a language is a file that writes a path, the way adding a device is.

pine.ts.runtime holds no list of grammars. It asks *grammar-of*, which
pine.ts.syntax sets to read the declaration, so what grammars exist is written
rather than compiled in. Grammar shared libraries are Guix packages (see
guix/tree-sitter-commonlisp.scm) loaded off the search path by name; Guix puts
them under lib/tree-sitter/, not lib/, so grammar-library-candidates checks
there plus pine's own tree.

* Runtime

- ts-runtime : libs-loaded flag + a languages hash. One per server (server
  slot ts-runtime).
- ts-entry   : a loaded language = its TSLanguage pointer and a parser.
- parse-state : per buffer. Its own parser, its persistent tree, the byte index
  the tree was read through, the band those cover, and the highlight cache.
- ensure-ts       loads libtree-sitter once.
- ensure-language loads a grammar once, memoized in the runtime. Unsupported or
  missing grammar -> nil (highlighting and motion just no-op; the editor runs
  fine without tree-sitter).

* The band

Past +whole-file-lines+ a buffer is not handed to tree-sitter whole. The cost of
a parse follows how many nodes the root holds, and a million lines of lisp is a quarter
of a million top-level forms: rebuilding that array per keystroke was 1.8s.

parse-lines! takes the :viewport a window is showing and slices the band around
it out of the line seq. That slice is the parser's entire input -- there are no
included ranges, and the byte index covers the band rather than the file.

- the band covers whole multiples of +band-lines+, so typing inside one leaves
  it where it is and the tree is shifted rather than rebuilt
- the tree, the index, and every position they report are relative to the
  band's first line. ps-offset is that line, and parse-highlights, parse-indent
  and parse-motion convert at the edge, so callers speak buffer lines
- a scroll changes the viewport while the line seq stays eq, so the band is
  what decides whether the tree still applies

The parse and the byte index never touch the lines outside the band. At a
million lines a banded parse costs 2.6ms and 1.5MB of resident set, against
5.4s and 2.9GB for the file.

* Highlighting: one walk over rules that are data

Supersedes the query-based flow described in "Highlighting" below. The query
approach over-tagged (every form head a call, every symbol a variable) and was
patched by capture-name-to-face + reclassify + a binding walk, with the winner
chosen by a face-priority table in render.lisp. Two defects followed from that:
name lookups sliced the character text with byte offsets, so any non-ASCII
earlier in the buffer corrupted later faces; and a namespace prefix was coloured
or not depending on whether its form sat in head or operand position.

The walker replaces the whole classification stack with one recursive pass over
the parse tree, in the model jinzo uses. It keeps everything else in src/ts.lisp
untouched: the FFI, grammar loading, the incremental reparse, structural motion,
and the byte<->char index.

  walk-highlights (root text index) -> ((line start-col end-col face) ...)

One visit per named node. It carries a context: the enclosing form's head
symbol, the form depth, the quote depth, and the set of in-scope bound
variables. Every token gets exactly ONE face, resolved during the walk, so no
render-side priority table decides syntax any more. Byte offsets from a node
become character positions through the index at emit time; the text is never
sliced by a byte offset, so the encoding defect cannot recur.

What the walk does at each node is a RULE, and the rules are data. A node rule
takes :face :role :inner :delimiters :head :fields :shape :rest :quote; a head
rule takes :face :name-face :shape :rest :indent. :shape is a map from element
position to ROLE, and the roles are the fourteen things a position can be --
:form :body :here :quoted :skip :operand :package :name :binding-name :bindings
:binding :vars :var :lambda-list :types :slots :slot. Each was a local function
of the hand-written walk this replaces; anything in a :shape or :fields position
that is not a role names a face.

Body-ness is derived, never declared twice: a rule that walks what follows as a
:body is a rule that indents it as one, so body-form-p and parse-indent read one
source and cannot disagree.

Scheme is data and no code at all. That is the proof the decomposition is right.

What is NOT written down is what a symbol IS. The daemon holds the code, so it
is asked: macro-function says a head is a macro rather than a call, and the
&BODY position in its lambda list is exactly emacs's indent N -- said by the
macro itself where the old walker guessed from a "def" prefix. special-operator-p
and constantp cover the rest. That is ~250 hand-typed symbol names deleted, and
the image knows the user's own macros too. A name the image has never heard of
falls back to the shape of the name, which is what editing a file this image has
not loaded is. The old per-language classify step read:

  classify-cl     : owns *cl-special-forms* *cl-builtins* *cl-constants* and the
                    binder tables; decides a symbol by head-vs-operand and by
                    binding scope. A form head that is a special form/macro is a
                    keyword; a binder head (let, dolist, ...) is a keyword and
                    its bound variables are variables; a builtin head is builtin;
                    any other head is a call; an operand symbol is a variable
                    (or a constant). A package_lit paints its package prefix
                    :namespace and its symbol by the same head/operand rule, the
                    same way in every position.
  classify-scheme : its own smaller ruleset.

Rainbow delimiters (:delimiter.N by form depth) fall out of the walk for free.

The query path is dropped, not because a good query is impossible, but because
this binding evaluates no query predicates (only ts_query_new/cursor/next_capture
are bound, none of ts_query_predicates_for_pattern), so predicate-driven queries
(#eq?/#match?, as upstream commonlisp/scheme queries use) do nothing here. A
walk also does what queries structurally cannot: track binding scope, quote
depth, and form depth, so bound variables, def names, and rainbow delimiters are
resolved from context, not pattern. Grammar loading no longer requires a query;
the grammar still loads for parsing and motion.

Checkable headless with `make hl FORM='...'`, which prints each token and its
face, so every rule and the binding/namespace/unicode cases stay regressions.

* Which grammar a buffer is parsed with

A lisp file is not always Common Lisp. pine's reader adds brace maps, bracket
seqs, paths and interpolation, and a file that declares
=(in-readtable pine.path:syntax)= is a different language: under it =/= is a
terminating macro character, so =(/ a b)= is a path where plain CL reads
division. That is why =pine= is its own grammar rather than a widening of the
Common Lisp one, generated from the same checkout as a dialect of it.

The readtable chooses. =/buf/?name/readtable= is inferred from the text the way
the package is, and =/mode/?name/grammars= maps a named-readtable to a grammar,
so a config with its own =defreadtable= says what parses it by writing one leaf.
=%grammar-of= asks the readtable first and the mode second; a buffer whose
readtable moves gets a new parser, because a parse-state binds its language when
it is made.

Where a file is can say what it is: =/mode/?name/paths= is globbed against the
whole namestring and asked before =:files=, because a config is written in
pine's reader and nothing about its name says so.

* byte <-> char (UTF-8), without a flat string

tree-sitter asks for bytes at an offset; the buffer is an fset seq of lines and
the cell grid and point are in characters. pine.ts.index is the map between
them, and it never builds the string: build-index walks the band once into a
per-line offset array, and an edit inside a line records a pending shift rather
than rebuilding.

source-line-col, source-byte, source-substring and source-char-at are the four
questions the walks ask. Each counts UTF-8 widths across the line, so a
multibyte character earlier on a line does not shift highlight columns or motion
targets. The count is carried forward per line, since a walk emits spans left to
right -- and the pair it carries is the byte offset OF the column it reached,
which is not the byte it was asked about when that byte falls inside a
character.

* Structural navigation

parse-motion walks the buffer's own persistent tree and answers a target; there
is no reparse and no flat string. The buffer sends :ts-motion to its parser and
takes :move-point back, so a structural jump in a large buffer waits on nothing
in the buffer's receive. call-with-root remains for a caller holding a string
rather than a buffer.

| command            | node walk                                                       |
|--------------------+-----------------------------------------------------------------|
| forward-sexp       | named node at point -> next named sibling's end (or parent end) |
| backward-sexp      | mirror: previous named sibling's start                          |
| beginning-of-defun | climb to the node of root it sits in (top-level form), its start          |
| end-of-defun       | same form, its end                                              |
| mark-sexp          | set mark, then forward-sexp                                     |

Bound under C-M-f / C-M-b / C-M-a / C-M-e / C-M-space in text-mode. lisp-mode
carries :ts-language :commonlisp; a buffer in it gets highlight + motion.

* Threading

A buffer with a language owns a parser actor, pinned to its own thread. An edit
commits and paints at once and tells the parser; the answer arrives later as
:highlights, :indent-region or :move-point. A buffer's receive never waits for
tree-sitter, and a parse fault parks that one actor while the buffer keeps
taking edits and painting its last good colours.

One request is in flight per buffer, with a dirty flag for the rest, so a
typing burst costs one parse per completed parse and the parser's mailbox
cannot grow behind a slow file. An answer carries the tick it was computed for
and is dropped when the buffer has moved on.

Buffers are only ever mutated through their actor; tree-sitter reads text,
never writes. Nothing on the edit path builds a flat string: the parser reads
the line seq through a TSInput callback and a byte index.

* Not done

- Every node call crosses cffi-libffi as a by-value TSNode, which costs 2.7us
  and allocates 1664 bytes. The highlight walk makes about 56 of them per
  source line, so a walk is ~93KB and ~166us per line and that is the dominant
  cost left. A pointer-taking shim over the dozen calls the walks use would
  take the allocation to zero.
- Type dispatch is a fresh lisp string per node and up to fifteen string= per
  walk step. ts_node_symbol answers a uint16; the names this file cares about
  could resolve to ids once per language.
- Language injection: a markdown document whose code blocks are highlighted as
  the language they name. The grammar parses the forms; merging a second
  parser's highlights over injected regions is the next capability.
- LOOP's hash-table extension (=:being :the :hash-keys :of=) is not in the
  commonlisp grammar, so src/provider/backlight.lisp still has ERROR nodes. It
  fails identically under =:commonlisp=, so it is upstream's rather than
  pine's reader; tests/ts.lisp names it.

#+TITLE: pine: project awareness
#+AUTHOR: Bret Horne
#+OPTIONS: toc:2 num:t

STATUS: nothing here is built, and it was argued before the namespace rewrite.
The question it asks still stands; the answers it writes are in the old
vocabulary -- =ask= targets and store keys -- and what it wants is a subtree and
the three verbs. Read =new-api.org= for the language it would be written in.

* Why this document exists

pine has no notion of the codebase a buffer belongs to. find-file
completes over the filesystem from the buffer's directory; M-. asks
the image about a symbol without knowing which system it belongs to;
search is external. Version control (vc.org) and intelligence
(intelligence.org) both require the same three answers before they can
be built: where the buffer's codebase begins, which files belong to
it, and, for Lisp, which ASDF system it constitutes. This document
specifies the layer that answers them.

* What we take from prior art, and what we do not

Emacs's project.el settled on a workable shape: a project is
discovered from a buffer rather than configured; the version-control
root answers the root question in almost every case; the file list
respects the VCS ignore rules. pine keeps all three. It omits: a
project file format of its own (the repository already defines its
boundary), a user-maintained registry of known projects (the store's
recent-files list already records what is worked on), and eager
indexing (every answer below is computed when asked; caching, if any,
is an optimization inside the git agent).

* The model

A project is derived from a buffer, on demand:

  root     the enclosing git worktree root when there is one;
           otherwise the nearest ancestor containing a marker file
           (*.asd, Makefile, manifest.scm); otherwise the buffer's
           directory
  files    the tracked and untracked-but-not-ignored files under the
           root. When the root is a git repository, the git agent
           answers (a status walk libgit2 performs natively);
           otherwise a filesystem walk
  system   for Lisp buffers, the ASDF system whose source tree
           contains the file. The daemon is a Lisp image and asks
           ASDF directly: registered systems and
           asdf:system-source-directory, plus .asd files found under
           the root

No configuration is stored. Per-project state -- a last search, a
per-project file history -- lives under store keys of the form
(:project ROOT ...), following the conventions in pine-user.org.
State and configuration remain distinct: the former is written by
use, the latter does not exist at this layer.

* The verbs

A :project ask target beside :server and :client (dispatch in
buffer/buffer.lisp; documented in api.org):

  (ask :project :root)       root for the current buffer
  (ask :project :files)      the file set, relative namestrings
  (ask :project :system)     ASDF system name, or nil
  (ask :project :describe)   the verb list

The target resolves through the current buffer's :pathname local. A
buffer without a pathname (scratch) answers relative to the daemon's
working directory, so callers need not special-case it.

* Surfaces

- project-find-file: completing-read over (ask :project :files) with
  :history :files, bound beside find-file.
- project-search: a pine.core.jobs job running rg at the root; results in a
  UI buffer of hits (file:line and match text); Return jumps via
  find-file and move-point, and the match region is propertized in the
  target buffer (properties.org). The hits buffer is built with
  show-layout like other tools.
- load-system / test-system: for Lisp projects, (asdf:load-system
  (ask :project :system)) through the one eval path, so compiler
  conditions reach the debugger and, once intelligence.org is built,
  compiler notes become diagnostic properties.
- The modeline is unchanged here; the branch segment specified in
  vc.org covers project identity, since root and repository coincide
  in practice.

* Ties

- vc.org: repository discovery and root discovery are the same walk,
  and the git agent produces the file set when the root is a
  repository.
- intelligence.org: :definition and :references scope their
  tree-sitter searches to (ask :project :files); the image producer
  uses :system to resolve definitions across a system's files.
- store: recent-files and save-place remain global; project-scoped
  state keys under (:project ROOT ...).

* Open questions

- Whether :files answers namestrings or (namestring . plist) pairs
  once vc wants per-file status from the same walk. The git agent
  computes both in one pass, so the verb's shape follows its first
  two consumers.
- Whether system mapping reports only systems loaded in the image or
  also systems findable from .asd files under the root. Loaded plus
  findable is the likely answer, since load-system is available.

#+TITLE: pine: version control
#+AUTHOR: Bret Horne
#+OPTIONS: toc:2 num:t

* Why this document exists

Version control state is part of every working session: the current
branch, what changed, who wrote a line, what happened in history, and
staging and committing without leaving the editor. This document
specifies how pine provides these, which backend it uses, and where
the boundary between backend and editor lies.

* What we take from prior art, and what we do not

Emacs's vc-mode is a command set dispatching over many backends (RCS,
CVS, SVN, git, hg), which limits every backend to the intersection of
their capabilities. magit took the opposite approach -- a git-only
interface exposing git's actual model, including hunk-level staging
and history rewriting -- and became the standard. The conclusion pine
draws: an abstraction over backends should not be designed before a
second backend exists, and must not cost the first backend its depth.

pine therefore builds no VC dispatch layer. The role of a generic
layer is filled by primitives that already exist: branch and dirty
state are refs feeding modeline segments and desktop widgets; hunks
and blame are region properties (properties.org); status and log are
UI buffers with actions; operations are commands. A version
control backend produces data for those surfaces and nothing else.
git is the first backend and is built to git's full model; if a
second VCS is ever added, it is another producer, and any shared
shape is factored then.

Omitted: parsing porcelain text output (libgit2's structures are the
interchange format), reimplementing git plumbing in Lisp, and any
command named vc-anything.

* The backend: libgit2 in a process agent

git operations run in a supervised process agent (pine.core.actor: spawn,
supervise-agent, and the debug hook that surfaces an agent's
conditions in the editor by name), calling libgit2 through CFFI.
Placing the FFI in an agent bounds the damage of a fault in the C
library: the supervisor respawns one agent process, and the daemon
holding the buffers is unaffected.

Packaging follows the usual rule: libgit2 enters through guix (it is
packaged upstream; the manifest grows one line), the CFFI bindings
live in the agent's code, and neither the daemon nor the frontends
link libgit2.

All results cross remoting as readable data:

  status   ((PATH :state :modified|:staged|:untracked|:conflicted) ...)
  branch   (:branch NAME :ahead N :behind N :dirty BOOL)
  hunks    per file: ((:from L :to L :kind :add|:delete|:change) ...)
  blame    per file: ((LINE COMMIT AUTHOR TIME SUMMARY) ...)
  log      ((COMMIT AUTHOR TIME SUMMARY) ...), paged by ask arguments

Writes -- stage, unstage, commit, checkout -- are agent asks with the
same data discipline. The agent watches nothing; every answer is
computed when asked, and the editor asks on events it already has:
save, buffer switch, UI buffer refresh.

* Surfaces

- Modeline: a branch segment fed by a ref (defref :vc-branch) that
  the editor updates on save and buffer switch, with a dirty marker.
  The modeline row reads the ref like any other source.
- Hunk indicators: on save and on find-file, the agent's hunks for
  the buffer's file become :until-edit properties with hunk classes;
  the stylesheet determines their appearance. next-hunk and prev-hunk
  walk them via (ask BUF :properties :class).
- Blame: a command that propertizes every line :sticky with commit
  data. When point enters a line, the echo area shows author, time,
  and summary from the property payload ((ask BUF :properties :at)).
  Invoking the command again clears the properties.
- Status buffer: show-layout rows over the status data. Return visits
  the file; s and u stage and unstage through agent asks; c opens the
  commit prompt (prompt with :history :commits) and commits. Rows are
  rebuilt from a fresh ask after every action; there is no cached
  model to go stale.
- Log buffer: show-layout over the log data; Return shows the
  commit's diff in a buffer whose changed regions are properties.

* Ties

- project.org: repository root discovery and project root discovery
  are the same walk; the agent also produces the project file set.
- properties.org: hunks, blame, and diff views are consumers; vc adds
  no display mechanism of its own.
- store: commit message history under :commits; per-repository state
  under (:project ROOT ...) keys.

* Open questions

- Whether the agent holds one libgit2 repository handle per root or
  opens per ask. Handles are cheap to open, and the stateless shape
  survives agent respawn without recovery code; measure before
  caching.
- Interactive rebase and history rewriting are not yet specified;
  they wait until the status/commit loop is in daily use. The
  omissions above apply to them as well.

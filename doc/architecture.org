#+TITLE: pine: the point, and the shape it takes
#+AUTHOR: Bret Horne

* The one idea

Pine is the Lisp Machine you cannot crash and can distribute.

Genera ran a whole operating system in one Lisp image: the editor, the network,
the window system, all of it live and redefinable from inside while it ran. An
error did not kill the machine. It dropped that one process into the debugger
while everything else carried on, and you looked at the frames, patched a
definition, took a restart, and went on. That is the part to keep.

What it did not have is a hard boundary. One address space on one machine: a
runaway allocation took everyone down with it, and a computation could not live
somewhere else. Emacs kept the malleable world and dropped the concurrency
instead: one thread, so a loop in elisp freezes everything, and one process, so
there is nowhere to put anything dangerous.

Pine wears the daemon shape emacs wears, and its ancestor is the Lisp Machine.
It restores the concurrency, and adds the boundary: a computation can live in
another image, on another machine, and when it faults its restarts come home to
the debugger you are sitting in.

* An operating system is a class hierarchy and a protocol

Five abstractions, and one hierarchy under =node= that carries them all.

: node                     a name, where it sits, what is under it
: |- value                 holds one
: |- derived               works one out, and follows whatever it read
: |  \- surface            works out a widget tree; a role says where it goes
: |- mount                 a namespace from somewhere else, grafted in
: |  |- directory          a directory on this machine
: |  \- peer               another pine, here or on another machine
: |- job                   something that runs
: |  |- thread             blocks on something
: |  |- actor              takes messages in order
: |  |- program            an os child that is not lisp
: |  |- image              a lisp we can evaluate in
: |  \- system             a package pine loaded
: \- document              text, and the structure its mode gives it
:    \- region             a span of one, with its own sub-regions

A =peer= is an =image= and a =mount= at once. That inheritance is the whole
reason this is CLOS and not a pile of structures, and it is what makes =mount=
one generic for a directory on this machine and for a pine on another.

** Memory, and storage

: (contents node) (setf (contents node) v) (nodes node)

=resolve=, =full-name=, =leafp= and =attach= are functions over =nodes=, so
they cannot disagree with it. =savedp= and =livep= are properties of a class,
not questions to re-answer per instance.

A =value= holds one. A =derived= records what it read while working one out, so
a write invalidates exactly what depended on it and nothing subscribes to
anything. =derived= takes a function for writing as well as reading, which is
why a device reading is a table row rather than a class:

#+begin_src lisp
  (device "audio"
          (list (list "volume" #'level (lambda (v) (sh "wpctl ... ~d%" v)))
                (list "muted"  #'muted #'toggle)
                (list "sinks"  #'sinks (lambda (v) (sh "wpctl set-default ~a" v)))))
#+end_src

A row may answer a list. =/dev/audio/sinks= is every sink there is,
=/dev/net/wifi= is everything in the air, and writing one a name is what picks
it. What is under a device is what it can be asked, not a subtree to keep in
step with the machine. =/dev/clip/text= is the desktop's clipboard the same way:
reading it is what anything else copied, writing it is copying.

A device is told the world behind it moved -- by a stream it named, or on its
interval -- and telling it means telling its rows. A device moved without them
is a clock that reads the hour once and never again.

Storage is not a layer. =savedp= is a property of a class; writes go through as
they are made, so a crash costs what happened since the last write; loading the
code builds the shape and the store only puts values back into nodes that
already exist. The host filesystem is in the namespace on the same protocol, so
a file is one of several places a thing can live, and so is a node on another
machine.

** Processes, and concurrency

: (start job) (stop job) (alivep job) (tell job m) (ask job m)
: (evaluate image form) (take fault restart) (resume image fault restart)

One triple for a thread, an actor, an os child, another image, a peer and a
loaded system. One method table. =start= on a system is what replaces every
install called by hand in a fixed order.

One actor system per image, made whether or not remoting is on. Something that
takes messages in order is an actor; something that repeats is a tick on that
system's wheel; a thread is made only where a call blocks. Nothing sleeps in a
loop and nothing takes a lock.

** Failure is a value you can act on

=fault:attempt= runs work and keeps what broke. With the debugger on, the
thread stops where it faulted and stands there holding its restarts, so what
you are offered is what is really still there. Taking one resumes that thread.

Across images it is the same act: a child image stands in its fault and says
what it is offering, the fault joins this image's own as a =borrowed= one that
knows where it stands, and taking one of its restarts is sent back to the
thread standing there. Over a pipe and over the network, one act.

** The interface

: (parts widget) (measure widget medium w h) (arrange widget medium x y w h)
: (paint widget medium) (anchor role width height) (text-size medium text font)

=parts= is a slot on the widget, so measure, arrange, paint, hit testing and the
wire cannot disagree about what a container holds. =paint= specializes on what
it is painting onto -- a grid of character cells, a cairo canvas -- so there is
one paint generic and not one per back end.

A =role= is a class, and it is the whole of what "any kind of surface" means.
=anchor= says where a new kind goes and =asks= says whether it waits to be asked
for: a bar is up as soon as it is declared, a panel is not. Nothing that shows a
surface needs compiled-in knowledge of either: what the role answered is a plist
of edges, sizes and margins, and it travels with the surface. There is no
privileged surface. The editor's window, the bar and a panel are the same class
with different roles.

A style rule names classes and nothing else. Pine draws widgets, and a widget
has no parts to reach into, so =.slider trough highlight= cannot fire and pine
drops it rather than leave it looking live. A rule matches the widget wearing
the class, not what is inside it. A slider's track is its background colour and
what it has filled is its colour.

A widget is *not* a node. It is an immutable value that crosses a wire. Nothing
you draw is in the namespace; only the surface that works it out.

** Text, and the elevated buffer

: (press mode d key) (insert mode d string) (indent mode d line)
: (complete mode d prefix) (save mode d) (structure mode d)

A mode is a class, so the chain is class inheritance, =call-next-method= is the
fallback, and precedence costs nothing:

: mode
: \- text
:    |- prose -- org
:    \- code  -- lisp -- pine
:               \- scheme

A terminal is a =document= and a =thread= at once: a program's screen is text a
window shows and a command acts on, and a pty read is where something blocks.
The mode is what makes a key go to the program rather than into the text.

What is laid over the text without being in it belongs to the document too. A
=span= is =(line from to face)=: a search that has just landed says one, a parse
says a whole file's worth, a terminal says one per run of colour its program
asked for. All of them are the same few numbers a cell is painted with, so the
grid paints a syntax highlight and an =ls --color= the same way.

An emacs buffer is characters with a flat property list laid over them. A pine
=document= is text plus the structure its mode gives it, and *the structure is
in the namespace*:

: /text/init.lisp                      the text
: /text/init.lisp/defsurface/bar       the form, as a region
: /text/init.lisp/defsurface/bar/icon  a sub-region of it

A =region= is a node whose contents is the text it covers, whose nodes are its
sub-regions, and writing it replaces that span. Marks, overlays, the parse and
what a command acts on are one thing: regions with identity, that survive edits
around them.

* Nothing is special

You define classes and methods in your own package, and pine loads it the way it
loads its own. =pine/user= is that package's whole vocabulary: Common Lisp and
pine's protocol together, rebuilt whenever a system is loaded, so a system loaded
later brings its own words with it.

The editor, the desktop, the window manager and the machine's own devices are
written exactly this way and name nothing your package cannot name.
=examples/notes.lisp= is an app of that shape -- its own kind of node, its own
mode, its own role and surface, its own commands and chords -- and the suite
checks that nothing under =src/= names it. Taking one away takes its surfaces and
its commands with it:

: pine use desk
: pine drop desk

* The shape of a running pine

| the daemon  | the tree, the systems it loaded, the store, and its screen     |
| /proc       | what it is running, readable and stoppable: the screen is there |
| the cli     | reads and writes of the daemon's tree, from a terminal          |
| an image    | another sbcl pine spawned, evaluated in, whose faults come home |
| a peer      | another pine, here or elsewhere, mounted and evaluated in       |

The screen is not a second program. A surface is declared and shown, and pine
paints it: the tree the surface worked out goes onto a cairo canvas over a
wayland surface, through the same =paint= that puts a widget on a grid of cells.
The connection blocks, so it is a =thread= and hangs at =/proc/screen= like
anything else that runs. Nothing to launch, and nothing between a surface and
its pixels.

On a compositor that manages its own windows, pine is a client of it: a bar is a
layer surface, a window is an xdg toplevel, and =/wm= is what that compositor
says about itself. On one that asks for a window manager, pine is that too: it
says what the compositor handed over at =/wm/said=, and puts each window where
=/wm/placement= says. Writing that place is the whole of being a window manager:
core has outputs, windows and what has the keyboard, and holds no opinion about
how any of them are arranged. See [[file:wm.org][doc/wm.org]].

Being the window manager is what makes the rest of it work there rather than a
separate world: pine binds the compositor's layer shell support, so its own bar
maps the same way it does anywhere else, and the compositor tells it what area is
left after that strip -- which is the area a layout is given. One bar, one
namespace, two compositors.

The wire is for the other case. =/surface/<name>/wire= is the tree written down
as plain data, so a pine that mounted this one over the network can show its
surfaces from another machine. That is what =mount= and =peer= are for. It is
not how a surface reaches the screen in front of you.

: make daemon      # a pine in this terminal, on the compositor you are under
: make screen      # one on a headless compositor, and a capture of the result

* The config is Lisp

=~/.config/pine/init.lisp= is read by the daemon, in =pine/user=, with pine's
own readtable so a path is a literal. It is the same language and the same
tree, so a surface reads a node and a click writes one. See
=examples/init.lisp=, which the suite loads so it stays a config you can copy.

: (use :host)                            load a system and start it
: (device "media" :player "emms")        put a device under /dev and follow it
: (write /wm-terminal "alacritty")       a place nothing has made yet is made
: (defclass ticker (overlay) ())         a kind of surface
: (defsurface ticker (:as 'ticker) ...)  one, declared
: (defmethod setting ((m text) k) ...)   what a mode says about itself
: (bind 'text "C-c h" "hello")           a chord, in a mode and under it

A read finds what is there. A write makes what is not.

To look at what a config draws, with no display and no compositor:

: make shot CONFIG=~/.config/pine/init.lisp

* Where the code is

The substrate is three directories, and nothing else:

| =src/data.lisp= | values, boxes, tables: fset and sento.atomic, named nowhere else |
| =src/fs/=       | node, derived, tree, path, mount, store: memory and storage       |
| =src/run/=      | jobs, actors, faults, commands, images, peers: processes          |
| =src/ui/=       | widgets, layout, hit testing, styles, surfaces, the wire          |

Loaded on top, privileged by nothing:

| =src/text/=    | documents, modes, and tree-sitter behind them |
| =src/host/=    | the machine's own devices, at =/dev=          |
| =src/edit/=    | windows onto documents, and the chords        |
| =src/desk/=    | a bar, and the panels it opens                |
| =src/term/=    | programs with screens of their own            |
| =src/wm/=      | the compositor, in the namespace              |
| =src/paint/=   | pixels, through cairo: the other medium       |
| =src/wayland/= | the display: pine's surfaces on a compositor  |
| =vt/=          | the terminal emulator                         |

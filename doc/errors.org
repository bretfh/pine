#+TITLE: pine: conditions, errors, and the debugger
#+AUTHOR: Bret Horne
#+OPTIONS: toc:3 num:t

* Why this document exists

architecture.org states the contract in one line: /no shared thread ever
blocks/, and /errors come home/: any image's error surfaces its restart menu in
the editor, by name, and is driven from there. It describes the cross-image
half of that (an agent's restarts ship home, the editor drives the choice back)
and calls the in-image and cross-image debugger "the same code with one remoting
hop inserted."

This document specifies the in-image half that architecture.org leaves implicit:
what a condition boundary is, where one wraps, what object an error becomes, how
many can be live at once, how a parked thread gets its restart choice back, and
how keyboard input reaches the debugger when the erring thread is not the thread
you type at. It also names the two places pine violates its own contract today
(a shared pool that a parked context would block; sources that swallow errors
into =(error () nil)=) and the topology change that fixes them.

The forcing observation: pine already has a real debugger for one path (an
evaluation on its own thread) and nothing for the others. An edit that signals
died silently inside the actor pump; a source that faults swallowed it; the
renderer had no guard at all. A Lisp Machine does not have paths that swallow.
Every context that runs code can drop into the debugger in its own live stack.
That is the target.

* The spine: cross-image live redefine and retry

pine is many images -- the daemon, the editor app, the desktop app, and every
agent and service you write to replace a tool on this machine, each its own SBCL
process over remoting. This split is BUILT (see architecture.org Status):
the daemon spawns and supervises the frontends, agents are real SBCL images, and
each frontend serves itself as an agent so the daemon can eval into it. The
debugger is not here to report faults. It is here so you can repair any of those
images while they run, from the editor, and continue.

The loop, end to end, across images:

#+begin_example
  a computation in image X faults
    -> X's boundary PARKS it: the operation is suspended with its restarts LIVE,
       on the blocked thread inside X, holding the extent where retry is possible
    -> the session COMES HOME: condition text + restart names + backtrace with
       source locations cross the wire to the editor (data, not the stack)
    -> you ATTEND it. the editor's eval target is now X. you jump from a frame to
       the failing definition and edit it in a pine buffer
    -> you RECOMPILE that defun INTO X: the form ships to X and compiles there, so
       X's heap holds the new definition and X's live callers use it
    -> you pick RETRY. the suspended operation re-runs in X, in the same extent,
       under the new code, having lost nothing else in X and nothing at all in the
       other images.
#+end_example

Same shape whether X is the editor's own image (in-process, the =pick-restart=
cvar), the desktop image, or a :process agent on another host (the =:resume=
remoting hop). One code path, one debugger surface; the remoting hop is the only
difference -- architecture.org's "in-image and cross-image debugger are the same
code with one remoting hop inserted."

What each piece needs, and where it stands:

- *park with live restarts* -- the condition boundary of this document. Built for
  the eval worker and the buffer actor in-image; the :process agent path already
  ships restarts home. Missing on the renderer, the sources, the pump.
- *eval target follows the attended session* -- architecture.org's "one eval
  path: run this in that agent." While you attend X's session, C-x C-e and the
  defun recompile go to X, not the editor's image. This is what makes "recompile
  into X" an ordinary keystroke, not a special command.
- *a retry restart on every retriable boundary* -- so "I fixed it, continue" has
  something to continue into. A buffer edit offers retry / abort; a source tick
  offers retry / skip / disable; an eval offers retry / abort. Without one, the
  only move after a fix is abort: the code is repaired but the operation is lost.
- *source locations across the wire* -- backtrace frames carry file + position so
  "jump to the failing defun" works when the fault is in another image; on a
  shared filesystem the jump is local once the location crosses.
The cross-image half is not blocked on infrastructure: the split, remoting,
agents, the ship-restarts-home debugger, and eval/compile-into-a-target all
exist. What is missing is the wiring above -- the session registry, the boundaries
on the renderer and sources, the retry restarts, and eval-target following the
attended fault. Those are the work, not the transport.

The isolation is what makes this a daily driver rather than a party trick: a
service you wrote and are mid-editing can fault, exhaust its heap, or segfault in
its own image, and the editor you are typing in and every other service stay up.
You repair the one that broke and retry it, or the supervisor restarts it while
you do. That is the combination the goal names: live repair of any part, with no
one part able to take the whole down. It is the within-image liveness of Genera
and Smalltalk with the between-image fault isolation and supervision they lacked,
which is why neither the shared-heap Lisp Machines nor crash-and-restart OTP is
the whole answer on its own.

* The rule, restated for a multi-thread image

emacs can afford one debugger design because it is one thread: the debugger is a
recursive edit, the same thread reads keys in a nested loop, and "block for a
restart" and "keep taking input" are one act. A Lisp Machine affords a different
one because every process can enter the debugger on its own live stack and the
window system routes the keyboard to that process's debugger window.

pine is neither. It is one image with many threads, and exactly one of them
(the session input thread) reads the keyboard. So the design has to answer a
question neither ancestor faces directly:

#+begin_example
  when a thread that is NOT the input thread errors,
  how does it show you a debugger and receive your restart choice?
#+end_example

The answer is the spine of this document: the erring thread parks and publishes a
/debugger session/; the input thread /attends/ a session and routes your
keystrokes to it; your choice travels back down the session's resume channel to
the parked thread, which invokes the restart in its own still-live extent. This
is "move the decision, not the handler" (architecture.org) applied to local
threads, not just remote images. The remote case is then the identical thing
with the resume channel crossing a wire.

* The contexts that run code

Every place code runs is a context, and each has a home thread. This is the map
the whole design is drawn against.

#+begin_example
  context              home thread            can it block safely?
  -------------------  ---------------------  ----------------------------------
  session command      session input thread   NO  -- it reads the keyboard; if it
                                               blocks it cannot drive its own
                                               debugger. recursive edit instead.
  buffer edit          a dispatcher thread    only if that thread is its own; on
                                               the shared pool, blocking violates
                                               the contract (see below).
  evaluation           its own eval thread    YES -- architecture.org: "the worker
                                               captures the restarts and blocks."
  renderer             a dispatcher thread     same problem as buffer edit today.
  data source          its own thread/process  YES per architecture.org, once
                                               sources are isolated agents.
  process agent        another SBCL image      YES -- parks in its image; restarts
                                               ship home; already built.
  remote frontend      another OS process       YES -- same as an agent.
#+end_example

Two rows are marked unsafe under today's topology (buffer edit, renderer) and
one is aspirational (data source, isolated). Fixing those is section "Parking
without blocking a shared thread."

* The condition boundary

A condition boundary is the wrapper every context runs its body inside. It has
one job: an unhandled error does not escape into the pump to be swallowed, and
does not drop to a console; it becomes a debugger session and the thread parks
(or, for the session thread, recurses). No context is exempt. The end of the
=(error () nil)= era is a boundary on the source loop, the render loop, and the
message pump, not a smarter =handler-case=.

The seed exists: =pine.core.eval:with-debugger= / =call-with-debugger= (core/eval.lisp)
wraps a thunk so an unhandled =error= is caught in the signal's own dynamic
context (=handler-bind=, so it wins before the actor pump's own handler can trap
it), builds the session, and blocks on a resume. Today it wraps the buffer
actor's =dispatch-message= and the eval worker. The design puts one on every
context in the table, each with the resume semantics its row allows.

Boundaries compose with the robustness floor already in architecture.org: an
unknown message tag still warns and drops, never errors. The boundary is for
code that signals, not for malformed sends.

* The debugger session object

Today =pine.core.eval:evaluation= is the error object, and two specials hold "the one
in the debugger": =*pending-debugger*= and =*pending-agent-debug*=. That is a
single-slot model. A multi-thread image faults in more than one place at once (a
source and a buffer, an agent and a command), so the object is promoted to a
first-class /debugger session/ held in a registry.

#+begin_example
  debugger-session
    condition        the condition, rendered to text (crosses a wire cleanly)
    condition-type   its type name
    restarts         the live restarts, by name + report string (data, not the
                     restart objects -- names are what cross images)
    backtrace        captured at the signal, while the stack was live
    origin           which context: buffer NAME / source NAME / agent / command /
                     renderer -- so the surface can group and label
    parked-thread    the thread waiting (nil for the recursive-edit case)
    resume           the channel the choice travels back through (a cvar in-image,
                     a remoting reply cross-image -- the ONE difference)
    policy           per-origin: how repeats collapse, what restarts mean
    status           :parked :resuming :done
#+end_example

=evaluation= becomes one producer of sessions, not the session itself. The eval
worker, the buffer boundary, a source, an agent, all produce the same object;
the surface and the resume path do not care which context made it.

* The session registry, and attending

Sessions live in a registry, not a pair of specials. The editor shows the live
ones and you /attend/ one at a time: the attended session is the one your
keystrokes drive. This is the generalization of what the agent path already does
for one remote error, to N concurrent errors from any origin.

#+begin_example
  +-------------------------------------------------------------+
  |  DEBUGGER SESSION REGISTRY                                   |
  |   #<session buffer:notes  type-error   parked>              |
  |   #<session source:audio  usocket err  parked  (x37)>       |
  |   #<session agent:build   unbound-var  parked  remote>      |
  +----------------------------+--------------------------------+
                               | the editor lists these; you attend one
                               v
  +----------------------------+--------------------------------+
  |  *debugger* surface (attended session)                      |
  |   condition, backtrace, restart list, the other sessions    |
  |   as a switchable stack                                      |
  +----------------------------+--------------------------------+
                               | pick a restart
                               v
  session.resume <- choice -> parked-thread invokes it locally
#+end_example

The =(x37)= on the source session is the policy at work: 37 identical faults
collapsed into one live session with a count, not 37 sessions. Without that a
faulting poll is a session storm. See "Per-origin policy."

* Input follows the error

The registry answers "what errored"; attending answers "where do my keystrokes
go." When you attend a session, the session input thread routes dispatch to that
session's debugger keymap instead of the underlying buffer. This is the Lisp
Machine move (the keyboard follows the debugger) done with pine's single input
thread: the thread does not move, the /routing/ does.

The one context that cannot use this is the session command, because its parked
thread /is/ the input thread; it cannot both wait for a choice and read the
choice. That context uses the emacs move instead:

#+begin_example
  session command errors on the session thread
     -> the boundary enters a RECURSIVE EDIT: a nested drain of the SAME input
        inbox that dispatches the debugger keymap, then returns to the outer
        command loop when you resume or abort.
#+end_example

So the session thread's debugger is a recursive edit (emacs), and every
off-thread context's debugger is attend-and-resume (Lisp Machine / the existing
agent path). They present as one surface. =debug-on-error= chooses, per command,
whether a session-thread error enters the recursive-edit debugger or just prints
to the echo area and continues -- the exact emacs knob, already wired.

* Parking without blocking a shared thread

Attend-and-resume requires the parked context's thread to actually park. That is
fine when the thread is the context's own (an eval worker, an isolated source, an
agent). It is a contract violation when the thread is a /shared/ dispatcher, and
today buffer actors and the renderer share one pool:

#+begin_example
  observed: message-box/dp, 4 workers, random strategy, shared across actors.
#+end_example

Park a buffer actor in the debugger and it holds one of four workers for as long
as you read the backtrace. The renderer is on the same pool, so the surface that
draws the debugger competes for the remaining three; enough concurrent parks and
the pool wedges. That is the original frozen-editor feeling moved one layer over,
and architecture.org already forbids it: "no shared thread ever blocks."

So the topology change this design depends on, stated as a requirement, not an
optimization:

- The renderer gets its own dispatcher (pinned), so drawing the debugger never
  competes with a parked context.
- Any actor that can park in the debugger owns its message thread rather than
  sharing the pool, OR the boundary hands the parked wait off the pool thread so
  the worker returns immediately. The first is simpler and matches the
  contract; the buffer actor's mailbox becomes its own thread the way the eval
  worker already is.
- Data sources are isolated agents (their own thread or process), which
  architecture.org already requires for the IO-blocking reason; the debugger
  requirement is the same requirement.

This is the item that turns "the debugger pops up" into "the debugger pops up and
the screen keeps painting while three buffers are parked."

* Per-origin policy

A boundary is not one behavior. What an error means, and what restarts it offers,
depends on the origin. The policy field carries this.

- *command* (session thread): =debug-on-error= nil -> echo the condition, the
  loop lives on (emacs default); non-nil -> recursive-edit debugger.
- *buffer edit* (off-thread): park with restarts =retry this edit=, =abort= (drop
  the edit, keep the buffer -- its prior fset state is intact because a handler
  commits state only as its last step). Never lose the buffer to a failed edit.
- *evaluation*: unchanged from today -- restarts as captured, =abort= the eval.
- *data source*: the honest replacement for =(error () nil)=. Restarts =retry
  now=, =skip this tick=, =disable this source=. Repeated identical faults
  collapse into one session with a count and a backoff, so a broken poll surfaces
  once with "37 times," not 37 times. A disabled source is a supervised state the
  registry can show and you can re-enable, not a silent dead feed.
- *renderer*: a render error parks with =retry the frame= and =skip the frame=;
  it must never take down the loop that draws every surface, and it must never
  swallow, because a renderer that silently drops frames looks exactly like a
  hang.
- *agent / remote frontend*: ship restarts home, drive the choice back over
  remoting. Already built; it becomes one more origin in the same registry.

* The debugger is the first structured surface

The current debugger buffer is text plus =*debugger-restart-lines*=, an alist
from buffer line to restart index, so pressing a number or Return-on-a-line can
find "the restart on this line." That is the raw-text fake: the buffer does not
know its lines are restarts and frames; a parallel alist does.

The debugger is the forcing case for a real model: a surface whose lines are
backed by objects (a stack frame, a restart, a nested condition), where point on
a line resolves to the object, keys act on the object, and the text is a
projection of the model rather than the model. That model is not
debugger-specific -- dired lines are files, jobs lines are evaluations,
completion lines are candidates. It is specified separately in surfaces.org; the
debugger is its first and most demanding instance, because its objects
(restarts) are live and its actions (invoke) are irreversible.

* What exists, what this designs

Built and running:

- =pine.core.eval:with-debugger= / =call-with-debugger=: the condition boundary seed,
  =handler-bind= based so it wins before the actor pump, with an always-present
  =abort=. Wraps the buffer actor's dispatch and the eval worker.
- =eval-debugger-hook=: the single debugger-entry; if no surface is installed it
  aborts rather than blocking forever (a parked thread with no way to be resumed
  was itself a hang).
- The command boundary: =%guarding-errors= + =command-error=, routing by the
  =:debug-on-error= variable (echo vs the surface), non-blocking on the session
  thread.
- The eval and agent debugger surface: =%show-debugger=, the restart menu,
  =debugger-mode=, the cross-image ship-home path.

Designed here, not yet built:

- The debugger-session registry replacing =*pending-debugger*= /
  =*pending-agent-debug*=; N concurrent sessions, attendable as a stack.
- Input-follows-the-error routing, and the session-thread recursive edit as the
  one special case.
- Condition boundaries on the renderer, the data sources, and the message pump --
  the end of every silent =(error () nil)=.
- The topology change parking requires: renderer on its own dispatcher; parkable
  actors off the shared pool; sources as isolated agents (shared with
  architecture.org's split-topology work).
- Per-origin policy, especially source fault collapse/backoff/disable.
- The debugger rebuilt on the structured-surface model (surfaces.org).

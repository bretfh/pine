#+TITLE: pine: region properties
#+AUTHOR: Bret Horne
#+OPTIONS: toc:2 num:t

* Why this document exists

pine has two annotation mechanisms today. Highlights (:set-highlights,
mode/edit.lisp) are runs of (line start end face) computed by
tree-sitter or installed by UI buffers; they style text, carry no
payload, and are replaced wholesale on reparse. Overlays (:overlay /
:clear-overlays, mode/edit.lisp) are per-line annotations stored in the
buffer meta under :overlays -- text rendered after the line, styled by
class, cleared by the next edit. Each was built for its first consumer.

The systems charted in systems.org need the general form of the same
idea. Compiler diagnostics attach a message to a column range of a
line; project search highlights match regions in visited buffers;
blame attaches commit data to each line; version control marks hunk
ranges. All of these are data attached to a region of a buffer, styled
by class, with a defined behavior under edits. This document specifies
that mechanism.

* What we take from prior art, and what we do not

Emacs provides two mechanisms with different semantics and different
performance characteristics. Text properties are part of the text:
copied text carries them, edits move them naturally, and reads are
fast. Overlays are objects beside the text, per buffer, with
priorities, before/after display strings, and their own keymaps, and
with well-known cost cliffs at large counts. Packages must choose
between them and often end up using both.

pine defines one mechanism. From the prior art it keeps: regions with
start and end positions that adjust under edits; an attached payload;
and appearance resolved through the style system -- here, classes
resolved by the one stylesheet that both the cairo painter and the
cell renderer read. It omits: keymaps on regions (behavior belongs to
modes and commands), before/after display strings (the existing
overlay rendering covers trailing annotation text; richer display is a
UI buffer's job), and priorities (a cell takes the classes of
every property covering it, and the stylesheet cascade resolves
appearance as it does everywhere else).

* The model

A property is readable data in the buffer's state:

  region   start (line . col) to end (line . col), end exclusive
  class    a keyword, styled via the stylesheet (defrules applies)
  data     a plist payload, any readable value; nil for pure styling
  policy   behavior under edits (below)

Properties are stored in the buffer state as :overlays is today: an
fset structure in the meta, updated atomically by the edit verbs in
the buffer actor. Consequently they ride every snapshot to every
renderer and every image without additional plumbing, and undo
restores them together with the text they annotate. There is no side
table and no separate notification channel; a property change is a
state change like an insertion.

The adjustment rules are specified, not left to the implementation.
An edit wholly before a property shifts it. An edit wholly after it
leaves it unchanged. An edit inside it grows or shrinks it. An edit
that removes the entire region removes the property. There are two
policies. Under :until-edit, any edit to the buffer removes the
property; this matches the current eval-result behavior and is the
correct default for anything a producer recomputes, such as
diagnostics and search hits. Under :sticky, the shift/grow/remove
rules above apply; this is for annotations that follow text, such as
blame data and bookmarks. Consumers needing other behavior recompute
their properties from their own source.

* The verbs

base-mode gains three verbs (mode/edit.lisp; api.org's verb table):

  (tell BUF :propertize :from (L . C) :to (L . C)
            :class K [:data PLIST] [:policy :until-edit|:sticky])
  (tell BUF :clear-properties [:class K])
  (ask  BUF :properties [:at (L . C)] [:class K])

:overlay and :clear-overlays remain as the line-shaped form: an
:overlay is a :propertize at the line's end with the annotation text
as data and :until-edit policy. Existing behavior does not change.
:set-highlights becomes a producer: the tree-sitter highlighter writes
its face runs through the same channel, which removes the last piece
of annotation state that does not live in buffer meta.

(ask BUF :properties :at P) answers what is at a position; it is how
help and intelligence surfaces show a diagnostic's message in the echo
area when point enters its region.

* Rendering

render-view-rows (render/render.lisp) currently merges highlight
runs into cell styles and appends overlay text after lines. It becomes
one pass over the properties visible in the window: class to style
through the shared resolution, trailing annotation data rendered where
overlays render today. Nothing changes for the frontend; styled cells
cross the wire as before.

* Initial instances

  eval results        :until-edit line annotation (existing behavior)
  ts highlighting     :sticky styling runs, producer-owned
  search hits         :until-edit styling, cleared by the next search
  compiler notes      :until-edit, condition text as payload
  active region       a property with a single consumer

* Open questions

- Whether the fset structure is a map keyed by region or an interval
  tree. Buffers with thousands of tree-sitter runs are the sizing
  case; the choice follows measurement and is private to the buffer.
- Whether :properties :at should report overlapping properties in
  class order. The first consumer that needs an order decides.

This is the reference manual for Pine. It explains the concepts you work with
and how they fit together. It is organized by concept, not by file. The prose
tells you the model first and the specifics second, so a chapter is worth
reading start to end once, then returning to for reference.

Three kinds of document sit beside each other in this tree, and it helps to know
which you are in. This manual, under =doc/=, explains the concepts and how to use
and extend them. The design notes under =design/= argue the rationale and the
internals: =philosophy.org= for the one idea, =architecture.org= for the shape
of the whole, =api.org=, =theming.org=, =client-actor.org=, =treesitter.org=,
=hacking.org= for their subjects. The living state of the work is in
=~/org/pine*=, not here. When a chapter has a deeper argument to point at, it
names the design note that carries it.

A word on how to read the names. Every subsystem is a package, and the package
name is the concept: =pine.buffer=, =pine.layout=, =pine.cell=. When this manual
says "the layout engine" it means =pine.layout=, and when it names a function it
gives the package, as in =pine.buffer:make-buffer=. You can follow any of them
into the source; the source is the final authority and this manual tracks it.

* Pine
:PROPERTIES:
:DESCRIPTION: The one idea, and what follows from it.
:END:

Pine is the Lisp Machine you cannot crash and can distribute. That one sentence
is the design, and every concept in this manual exists to hold it true. The full
argument is in =design/philosophy.org=; here is only what you need to use the
system.

Three commitments follow from the sentence, and they shape everything else.

The world is one live redefinable Lisp you inhabit while it runs. You do not
build Pine, launch it, and use the result. You start it and change it from
inside, redefining functions, themes, widgets, and commands in the running
image. Nothing in this manual describes a build step between an idea and seeing
it, because there is not one.

An error drops a computation into the debugger without taking the world down.
This is the Lisp Machine's error model, kept on purpose. A command that hits an
unbound variable, a source that throws, a widget that miscomputes: each fails in
place and is inspected and patched live, while the rest keeps running. When you
read later that a renderer "surfaces the error rather than swallowing it," this
is why. Silence is the bug; the debugger is the feature.

Computations live in their own processes, and the boundary between them can be a
hard one, across images and across machines. This is the axis the Lisp Machine
lacked and the one Emacs lost. In Pine the intelligence lives in a headless
daemon, and the things you see, an editor, a desktop, later a compositor, are
separate processes that attach to it. A frontend can die, or be killed, or run
on another machine, and the daemon and the world it holds survive. The next
chapter is about that shape, because it is the one you meet first and the one the
rest depends on.

* The Shape
:PROPERTIES:
:DESCRIPTION: Daemon, clients, and the attach protocol.
:END:

Pine is a headless daemon plus the clients that attach to it. The daemon holds
the world: the buffers, the evaluation, the reactive state, the widget trees,
the themes. A client holds none of that. It opens surfaces on a display, paints
what the daemon pushes to it, and sends back what the user did. The intelligence
is in one place; the frontends are thin and replaceable. See
=design/architecture.org= for the diagram and =design/client-actor.org= for the
actor detail.

** The daemon

The daemon is =pine.server:*server*= and the actor system that runs inside it.
It has no window and needs no display. Started with =pine:run-daemon=, it stands
up the buffer registry, the theme faces, the evaluation thread, the reactive
sources, and a listener that clients connect to. Everything with real state or
real logic runs here.

Concurrency in the daemon is actors, not locks in application code. An actor is a
mailbox with a thread behind it; you =tell= it a message and it processes
messages one at a time, so the state it owns is only ever touched from one place.
Buffers are actors, the per-client renderer is an actor, sources have actors.
This is how the daemon runs many things at once without the single-threaded
freeze that the one idea rejects.

** Clients and app kinds

A client is a separate process. It connects over the network (sento remoting,
loopback by default) and declares what kind of frontend it is. Today there are
two kinds, =:editor= and =:desktop=; the compositor will be a third. The daemon
keeps a table of app kinds, and each kind registers what to do when a client of
that kind attaches and what to do with the input it sends. This is
=pine.attach:register-app-kind=. The consequence worth holding onto: a new
frontend is a new kind and a renderer, not a change to the core. The wayflan
desktop and the wayflan editor were added this way, with the daemon untouched.

** The attach protocol and the wire

Attaching is a short asynchronous handshake, and it is worth knowing because it
is the seam the whole system folds along. The client tells the daemon's attach
actor "I am here, this is my display address, this is my kind." The daemon makes
a session for it, makes a per-client input actor, and tells the client back "you
are attached, here is the address to send input to." From then on the daemon
pushes frames or widget trees to the client's display, and the client sends keys,
resizes, clicks, and hints to its input actor.

Only plain data crosses the wire: lists, numbers, strings, keywords, vectors.
This is deliberate and it is what makes the frontends thin and the boundary hard.
A buffer's rendered frame crosses as rows of cells. A widget tree crosses as
=(type props . children)= forms, its click handlers replaced by integer ids; the
daemon keeps the closures and the client sends the id back when you click. No
Lisp object, no closure, no CLOS instance crosses. A frontend never holds a piece
of the daemon's mind, only a picture of it and a channel back. See the wire codec
in the layout chapter for the widget half of this.

* Buffers
:PROPERTIES:
:DESCRIPTION: The unit of editable content.
:END:

A buffer is a named piece of editable content and the actor that owns it. This
is =pine.buffer=. If you come from Emacs the word means what you expect: text you
edit, with a point and possibly a mark, a major mode, and local variables. What
differs is underneath.

** State, points, and marks

A buffer's state is its lines, its marks, its metadata, and a tick that counts
changes. The lines are an =fset= sequence, an immutable persistent structure, so
a state value can be shared and compared without defensive copying. Point is a
mark like any other; the mark that anchors a region is another. You do not mutate
a buffer's text in place from the outside. You tell the buffer actor to do it:
=(pine.buffer:tell buf :insert :text "x")=, =:delete=, =:replace-content=. The
actor applies the edit to its own state, alone, and moves on.

** Snapshots and subscription

Rendering never reads a live buffer. When a buffer changes it publishes a
snapshot, an immutable picture of the state at that tick: the lines, the point,
the marks, the syntax highlights. A renderer subscribes to a buffer and receives
these snapshots; it paints from the snapshot, never from the buffer itself. This
is the whole reason a buffer can be edited on its own thread while a frontend
paints on another and neither waits on the other. A snapshot in hand cannot
change underfoot.

** Highlighting

A buffer in a language mode carries syntax highlights, produced by the tree
sitter runtime (=pine.ts=, see =design/treesitter.org=) and attached to the
snapshot as a list of (line, start, end, face) spans. The renderer turns spans
into per-cell foreground colors when it builds the frame. Highlighting is a
property of the snapshot, computed on the daemon, so a frontend renders colored
code without knowing anything about parsers.

* Windows and Frames
:PROPERTIES:
:DESCRIPTION: How a buffer becomes a grid of cells.
:END:

A window is a view onto a buffer, and a frame is the grid of cells a client
paints. A window has a size, a scroll position, and the buffer it shows; the
renderer lays the window's visible lines into the frame's cells, adds the
modeline and the echo line, and the frame crosses the wire as rows. A cell is ten
numbers: row, column, character, a foreground triple, a background triple, and
packed attribute bits for bold, italic, and underline. This flat cell format is
the common ground every text frontend paints, whether the backend is a terminal,
a GTK drawing area, or a wayflan cairo surface. The cell grid is the wire format;
the backend is only the thing that ships it to a surface.

* Faces and Themes
:PROPERTIES:
:DESCRIPTION: Color and metrics as data.
:END:

A face is a named bundle of visual attributes, a foreground, an optional
background, bold, italic, underline, and a theme is a palette of color roles plus
metrics plus a set of faces that resolve against that palette. This is
=pine.buffer=, and the argument for doing it this way is in =design/theming.org=.

** Palette, metrics, faces

A theme is defined with =deftheme=. Its palette names colors by role, =bg=,
=accent=, =fg-dim=, not by hex at the use site. Its metrics name the layout
numbers, radius, border, opacity, the font. Its faces map a face name like
=:keyword= or =:modeline= to palette roles. You look up a color role with
=pine.buffer:color=, a metric with =pine.buffer:metric=, and a face's foreground
with =pine.buffer:face-fg=. Change the active theme and every face, every widget,
every rendered cell resolves against the new palette, because nothing downstream
holds a literal color.

** The rules: styling as data

Beyond faces, the desktop has a stylesheet, and it is data, not code. It is a
list of (selector, properties) pairs where the properties are CSS strings, kept
in =pine.buffer:theme-rules= so a single source drives every renderer. The GTK
backend flattens the rules to a CSS string. The cairo backend parses each value
and paints it directly. Both consume the same list, which is why the wayflan
desktop reproduces the GTK look without reinterpreting anything: same rules, same
radius, same glass. Styling as data is what let the whole GUI move backends
cheaply.

* The Layout Engine
:PROPERTIES:
:DESCRIPTION: Widgets as a measured, arranged, painted tree.
:END:

The layout engine is how Pine draws anything that is not a text buffer: bars,
panels, menus, pickers, the editor's own chrome. It is =pine.layout=, and it is
the piece to understand well, because the desktop, the apps, and the styling all
rest on it. See =design/layout.html= for the worked example.

** Nodes and the three passes

A widget tree is a tree of nodes, and it is drawn in three passes over a target.
MEASURE reports each node's natural size from the bottom up. ARRANGE assigns each
node an absolute rectangle from the top down, handing slack to the nodes that
asked to expand. PAINT writes each node into its rectangle. Separating the three
is what gives a real box model: alignment, expansion, and two dimensional
placement that a single linear emit could not. After ARRANGE every node has an
exact rectangle, so hit testing a click is exact too.

The same tree measures and arranges in two units. In cell mode a character is one
cell, and the tree lays out a text grid. When the dynamic variable
=pine.layout:*text-size*= is bound to a pixel measurer the identical passes lay
out in pixels, and the tree becomes a cairo drawing. One engine, two backends,
because the size of a piece of text is the only thing that differs and it is a
hook.

** The constructor DSL

You do not build nodes by hand. You write a terse tree with the constructors:
=column= and =row= for stacks, =label= for text, =icon= for a glyph, =button= and
=meter= and =ring= for controls, =boxed= and =centered= and =viewport= for
placement, =gap= and =rule= for space and lines. Leading keyword pairs are props
and the rest are children; a child that is a list is spliced, so mapping over data
composes the way iteration does in markup. A tree reads like what it draws.

** The wire codec

A widget tree does not cross the wire as itself. Nodes are CLOS objects and their
click handlers are closures, and neither serializes. So =node->wire= turns a tree
into plain data, =(type props . children)=, and replaces each handler with an
integer id, keeping the closure on the daemon under that id. On the client
=wire->node= rebuilds the tree, and where a handler was it puts a function that
sends the id back. Click a button on the client, the id travels to the daemon,
the daemon runs the closure. This is the widget half of the wire from the shape
chapter, and it is why a bar built from live daemon state can be painted by a
process that holds none of it.

** Hit testing

Because ARRANGE gave every node a rectangle, finding what is under a point is a
walk: =node-at= returns the deepest interactive node containing a line and
column, =click-thunk= turns a click into the action to run, =slider-value-at=
maps a click along a slider to a value. A frontend does not know what a button is.
It sends a coordinate, and the engine on the daemon decides what was pressed.

* Cells and Sources
:PROPERTIES:
:DESCRIPTION: Reactive state, and the world feeding it.
:END:

A cell is a named box holding a value that notifies when it changes, and a source
is something that keeps a cell current from the outside world. Together they are
how the desktop stays live without anyone wiring updates by hand. Cells are
=pine.cell=, sources are =pine.source=.

** Cells and views

A cell dedups on write: setting it to a value equal to the one it holds notifies
no one, so identical updates never cause a redraw. What makes cells reactive is
dependency tracking. When a widget builder reads cells inside a tracked render,
the render records exactly which cells it touched and subscribes to that set; the
next render re-subscribes to the possibly different set it touches this time. You
write a builder that reads =(cell :volume 0)= and it re-runs when the volume cell
changes and only then, with no manual subscription. This is =pine.cell:make-view=
and =render-view=, and it is the eww =var= idea made native.

** Sources

A source feeds a cell. A stream source runs a subprocess and sets a cell from its
output as lines arrive, event driven. A poll source sets a cell on an interval.
Either way the blocking work, the subprocess read, the shell call, runs on the
source's own thread, off the actor pool, so a slow or flooding source cannot
starve the daemon. Declared with =defsource= and =defpoll= and started together,
sources are the daemon's answer to the eww broker: the workspace list, the volume,
the network state, the now playing track, each a source feeding a cell that a
widget reads.

* Modes and Keymaps
:PROPERTIES:
:DESCRIPTION: How input becomes behavior. (to be written)
:END:

Major and minor modes (=pine.mode=), keymaps and key parsing (=pine.keymap=,
=pine.key=), and how the active modes layer their keymaps and their behavior. A
mode can also intercept dispatch, which is how a terminal buffer sends keys to a
pty instead of inserting them. To be written; the code is the current authority.

* Commands and the Minibuffer
:PROPERTIES:
:DESCRIPTION: Named actions and reading input. (to be written)
:END:

Commands (=pine.command=), how a key resolves to a command through the active
keymaps, and the minibuffer: prompting, and =completing-read= with its filtered
candidates and its callback. The palette shape, sources of candidates and acting
on the selection, is the natural extension point here. To be written.

* The Terminal
:PROPERTIES:
:DESCRIPTION: A pty in a buffer.
:END:

A terminal buffer is a pseudo terminal driven into an emulator (=pine.vt=) and
rendered as cells (=pine.term=). A reader thread appends the pty's output to a
pending queue; a per session pump asks the renderer to drain that queue into the
emulator and repaint, so the emulator is only ever advanced from the one thread
that also reads it. Keys in a terminal buffer are sent to the pty as escape
sequences rather than inserted, except the editor prefix so you can switch away.
The terminal is the clearest small example of the daemon owning a live thing and
a frontend only painting it.

* Rendering and Backends
:PROPERTIES:
:DESCRIPTION: From frames and trees to a surface.
:END:

Rendering is the daemon turning buffers and widget trees into the two wire forms,
and a backend is the client turning those forms into pixels on a surface. The
daemon side is =pine.render= (a buffer's frame to rows) and the cairo cell
painter shared by the frontends. The backends are the interesting part.

** The cairo backend

=pine.cairo= is a GTK free renderer. It binds =pine.layout:*text-size*= to a
cairo text measurer so the layout engine lays out in pixels, resolves each node's
style from =theme-rules= as data, and paints the tree: rounded backgrounds,
borders, themed text, sliders, rings, a calendar grid. It renders headless to a
PNG or live to a surface, and because it shares the layout engine and the theme
it reproduces the widget trees the daemon builds exactly.

** The wayflan backend

=pine.wayland= is a from scratch Wayland client, no GTK and no libwayland. It
binds =wlr-layer-shell= for anchored bars and panels and =xdg-shell= for windows,
paints the cairo trees into shared memory buffers, and drives input through the
layout engine's own hit testing. Its cost against the GTK backend is roughly two
gigabytes of dependency closure and the GObject introspection machinery, dropped;
what remains is cairo, sockets, and a little protocol code. This is the backend
the desktop and the editor run on now.

** The GTK backend

=pine.desktop-app= and the GTK editor are the original backend, GTK4 widgets and
the GTK CSS engine, kept as a fallback while the wayflan backend proves out. The
theme rules that the cairo backend parses, the GTK backend flattens to CSS. Two
backends, one source of style.

* The Desktop
:PROPERTIES:
:DESCRIPTION: Bar, echo, and panels.
:END:

The desktop is a set of named surfaces the daemon builds and a client paints: a
bar down one side, an echo strip along the bottom, and panels that toggle open,
calendar, audio, network, media, a control panel. This is =pine.desktop= on the
daemon and the wayflan or GTK backend on the client. Each surface is a widget
tree built from cells, serialized, and pushed; interacting sends an id or a hint
back and the daemon runs the closure or updates the echo. The desktop is the
layout engine, the cells and sources, and the wire, put together into the thing
you look at.

* Evaluation and Agents
:PROPERTIES:
:DESCRIPTION: Running Lisp, and processes with a boundary. (to be written)
:END:

Evaluation off the interaction thread (=pine.eval=), so a blocking or looping
form drops into the debugger without freezing the world, and agents
(=pine.actor=), computations that live in their own supervised processes with the
hard boundary the one idea calls for. To be written; this is where the "cannot
crash, can distribute" half of the sentence is implemented.

* Extending Pine
:PROPERTIES:
:DESCRIPTION: Writing a widget, an app, a source, a theme.
:END:

Every extension point in this manual is a small thing because the architecture
did the work. To add a status source, =defpoll= a cell and read it in a widget.
To add a panel, write a builder that returns a node tree and register it as a
surface. To add a command, define it and bind a key. To add a theme, =deftheme=
a palette, metrics, and faces. To add a whole new frontend, register an app kind
and write a renderer that paints the frames or trees the daemon pushes. None of
these touch the core, because the core was built to receive them. That is the
test of the shape, and it is the reason the manual is short.
